## 3. 环境选择与隔离设计

### 3.1 推荐完整 VM

| 候选 | 能取得的证据 | 取舍 |
|---|---|---|
| 完整 Linux VM，使用已有 Hyper-V、KVM 或 VMware 等后端 | 独立内核/PID 1、真实 systemd、受控电源事件、独立虚拟磁盘与实验网络 | **推荐**。优先复用已有平台，具体后端须在 G0 确认 |
| 普通容器、宿主 CI、WSL 或仅运行 Python 测试 | 可补充协议/模型证据；部分环境可运行 systemd，但故障域、内核和持久化条件不同 | 不替代本轮 L2/L3 VM 门槛，也不据此标记 Debian 12/13 通过 |
| 新租云 VPS | 可以做部分 Linux 验证，但引入采购、公网和目标误认风险 | 本方案不采用；需要另行选择和授权，不能借批准本方案自动创建 |

建议保留三个只读 OS 基础镜像，从中创建六个面板组合及按用例销毁重建的副本，不要求六台同时开机。规划估算为每 DUT（受测 VM）2 vCPU、2 GiB RAM、20 GiB 系统盘，另挂故障测试盘；辅助节点约 2 GiB RAM。初期至多并行两个 DUT。实际主机资源和快照增量在 G0 核实；这些是实验资源估算，不是产品最低配置承诺。

不在本轮安装虚拟化平台、WSL/Docker，也不假定当前 Windows 宿主已经具备某个后端。若现有平台不能完成指定断电/同步/休眠用例，记录 BLOCKED 并选择有该能力的隔离后端，不能静默跳过。

### 3.2 网络与身份

建立仅实验室可达的私有虚拟交换网络：DUT、合成代理客户端/流量端点、实验室 NTP/时间源、证据收集器。业务流量只往实验端点，不把公共网站或生产 VPS 当流量靶标。

1. 镜像/软件准备阶段与测试阶段分开。准备阶段仅经受控下载机取得 OS、固定面板/Xray 制品及系统依赖；核验后离线转入 DUT。测试阶段 DUT 无公网出口，阻断通往非实验网的 IPv4/IPv6 转发、宿主代理、VPN 路由、共享 SSH agent、生产磁盘与生产凭据挂载；实验客户端到 DUT、DUT 到指定实验端点/NTP 的精确白名单保留。
2. 若需要宿主管理通道，使用 VM 控制台或独立管理网络的明确端口白名单；不得桥接生产 LAN 或使用默认 NAT 自动放行所有目的地。
3. 证明隔离用虚拟交换机/防火墙规则和到**自建外侧哨兵端点**的拒绝记录；不向真实 VPS 发送“隔离测试包”。核对 IPv6 和代理环境也没有旁路。
4. 每个新 DUT 生成独立 machine-id、SSH 主机密钥、task_id、panel_binding_id、Client UUID 和面板 Token。新克隆身份须在生成配置前固定；已有任务的故障恢复副本不得为绕开绑定而更换身份。
5. 验收驱动须同时匹配 VM ID、实验室标记文件、machine-id 摘要、组合 ID、包摘要及预期网络。任一不符停止，不能靠只认 hostname 或 Remark 决定写入对象。

### 3.3 面板、TLS 与依赖准备

- 在 VM 中安装普通 systemd 形态的官方精确版本，实际二进制须位于 `/usr/local/x-ui/x-ui`，服务名为 `x-ui.service`。不使用 Docker、远程节点、全局推送或定制计量构建。
- 记录面板 tag、commit、下载来源、制品 SHA256、`x-ui -v`、关联 Xray 版本/摘要和安装方式。版本字符串只证明自报版本，来源仍需独立核对。下载入口为官方 [3.7.0 发布页](https://github.com/MHSanaei/3x-ui/releases/tag/v3.7.0)和 [3.10.2 发布页](https://github.com/MHSanaei/3x-ui/releases/tag/v3.10.2)；执行时选取并锁定资产，不使用浮动 latest 安装链路。
- OS ISO 同时核对版本、校验文件与签名；不能只看到下载 URL 含“24.04”就认定镜像版本。依照 [Debian 镜像验证说明](https://www.debian.org/CD/verify)及 [Ubuntu 镜像验证说明](https://ubuntu.com/tutorials/how-to-verify-ubuntu)。本次网页提取中 Ubuntu 24.04 目录标题曾与文件列表不一致，因此本文不指定未经确认的点版本/镜像摘要；G0 必须以已验签镜像和安装后 `/etc/os-release` 双重确定。
- 依赖至少包括 Python、curl、systemd/systemd-analyze、timedatectl、tzdata、CA 证书和校验工具。SQLite 一致性快照工具、故障注入和观察工具属于测试依赖，单独登记；只在实验室安装，不静默升级系统。
- 正常 API 链路使用实验室 CA 签发的 HTTPS 证书与实验域名，CA 只加入实验室系统信任库。客户端连接仍由工具固定到 `127.0.0.1` 或 `::1`；域名用于 Host/SNI，不解析到公网。**不使用 `-k`，不靠被工具清理的 CA 环境变量绕过验证。**r2 链路必须 HTTPS。
- 另覆盖明确允许的 loopback HTTP、IPv6 loopback、坏证书、错误主机名、重定向和代理环境负面用例；仅本机 HTTP 不能代替 HTTPS 正常路径验收。
- 为每个用例组创建独立 admin Token、面板实际支持的非管理权限 Token 和可撤销 Token，并登记两版面板实际 scope 名称与权限；不凭标签猜写权限，不使用生产 Token。隐藏输入和凭据文件权限依 P3 契约执行；不得记录 Authorization、stdin 凭据内容或原始密钥。

**代理业务的最小可行拓扑**：原生与旧来源样例均为本机 VLESS，正常功能链可先用隔离网内 VLESS/TCP，无公共握手目标。工具不检查传输层，业务结论只能覆盖实际测过的传输；若另测 REALITY，握手目标与证书/名称也必须为自建实验端点，不能沿用公网伪装目标。Xray 有效路由必须明确允许指定实验端点，不能因私网阻断规则而把代理不可用误判成工具缺陷；也不能为通流量放开所有出口。保存入站、路由、DNS、TLS 的脱敏有效配置，停用实验面板的通知/订阅抓取/更新等外部后台访问。以上均仅是批准后的实验环境准备，当前不执行。

配置准备先由实验面板建立对象，再以受控本机 GET 取得 record_id、UUID、关联关系，填入 P1 候选并执行离线校验和 discover；没有“仅给 Remark 就自动生成全配置”的现成入口。`provider` 可在原生小额度场景置 null；采用预算模型时必须让小额度样例同时满足预算约束。HTTPS 证书与 Token 的有效期应覆盖整个实验时间域。

## 5. 最小验收设施及证据能力

当前仓库的 `tests/run.py` 是 L1 模型入口，Linux 上直接运行它仍是 L1。`tests/loopback_transport.py` 只证明合成 HTTP 读取。**目前没有六 VM 编排器、真实系统故障注入器或完整自然账期验收 CLI；本方案不声称已有这些入口。**

确认后只补充验收必要的实验设施，放在单独测试目录并标明 `LAB_ONLY`，不向产品 CLI 增加 fake clock、force、retry 或绕过身份的选项。固定周期不缩为 30 秒/30 分钟；R1～R5 的精确时点按第 18 节取证。新增设施目前尚未实现，本轮不编写、不启动：

| 设施 | 最小责任 | 不允许替代的证据 |
|---|---|---|
| VM 运行登记与守卫 | 校验白名单、创建用例副本、记录 boot/session/case 身份，收集退出状态 | 宿主能创建 VM 不代表 guest 服务已生效 |
| 本机只读证据采集 | 调用现有 audit/check、采集限定 systemd 属性和 invocation 日志、比较受管文件/权限 | 不能仅以 CLI 的 PASS 或 service inactive 判定账期成功 |
| 合成代理流量端点 | 上传/下载固定校验内容，为指定 Client 产生可计量流量；观测连接扰动 | 真实实验代理可用不代表服务商流量口径已验证 |
| 受控本机 API 故障网关 | 在独立故障用例中转发至同机真实面板；仅一次转发，计数、延迟/丢弃响应、按阶段闸门 | 不伪造成功响应/confirmed，不把网关转发次数直接当数据库提交次数 |
| Linux 持久化/进程故障驱动 | 在专用测试盘或 disposable VM 上造成 ENOSPC/EIO/只读、进程中断、断电；观察原生锁及 fsync/rename | 源码 fault 回调只能证明带注入的接口路径，不能独立替代直接 CLI/真实内核故障证据 |

正常正向链路直接连接面板，无故障网关。故障链路须记录是否经网关、网关哈希和配置、真实面板版本。禁止自动 retry、代理重新提交和浏览器误点；按“工具尝试 / 网关接收 / 面板处理 / 数据库提交”分别计数。无法观察处理或提交时标记 UNKNOWN，不把零日志当零请求。

精确阶段故障可用现有依赖注入接口配合真实 POSIX 文件系统，也可由外部进程监督在持久化或 HTTP 阶段设置闸门；必须保留触发点证据。仅用轮询后随机 kill 而未命中目标阶段，不算该故障用例完成。跟踪 syscall 时只记录必要的文件、返回码与同步顺序，不抓取凭据 read/write 缓冲区。对生产模块的任何改动都应换新受测版本，而非藏在测试设施中。

### 5.1 原生故障与观测的落点

- **真实写故障**：专用虚拟块盘在安装前挂载到受测的固定状态目录，例如 `/var/lib/vps-kit/traffic`，保持属主/权限并记录文件系统、挂载和缓存模式；不靠 symlink 重定向固定路径。ENOSPC 要证明该挂载上目标写实际失败；只读挂载要观察 EROFS；EIO 可选本机内核支持的 device-mapper 错误目标，G0 先确认能力。`dm-flakey` 的 `error_writes` 与静默丢写 `drop_writes` 含义不同，本轮错误用例不能混用，见 [Linux 内核说明](https://docs.kernel.org/admin-guide/device-mapper/dm-flakey.html)。不填满宿主或 guest 系统盘，不用 root 下的 chmod 假冒 EIO/ENOSPC。
- **注入证据分层**：用回调抛异常只算接口注入；原版 CLI 在真实故障挂载上失败才算原生故障。记录确切路径/提交点，不能由 control 目录的磁盘故障推导 `/etc/systemd/system` 或发行目录也验证过。其他路径使用独立用例或明确标注接口证据，关键直接 CLI 的锁、正常同步、状态盘故障和中断证据不能被替代。暂时恢复只读可观测性属于实验处置，不删除临时文件/head，仍不重试原事务。
- **API 故障网关**：固定 loopback/端口的约束来自 [HTTP 适配器](../src/vps_kit/traffic/panel_http.py)。故障副本先把网关放到候选 URL 的 loopback 端口，真实面板放同机另一端口；冻结 URL/证书和后端后再创建任务或 r2 来源，不能执行中改活动 URL、端口或 Token 绕过绑定。网关仅一次转发，断开客户端后也不得重新提交。缺键/null/类型注入如被面板存储层规范化，可由这个明确标记的网关改一份 GET 响应；这属于响应故障，不能算真实数据库升级证据。
- **请求尝试的独立观察**：正常链路不插网关，可在 guest 观察真实 `/usr/bin/curl` 的 exec 事件，只保留 method、端点类别、对象摘要、PID/invocation 与时间。当前 Token 经 stdin 传入，禁止抓 stdin、环境凭据或完整 URL；URL/对象只在采集器内解析并脱敏。观察到 curl 启动只证明一次传输尝试，不证明服务端提交。无可靠计数器或命中点证据时相应子用例 BLOCKED。
- **服务器证据**：能取得面板处理日志或可区分的 DB 前后状态时分别记录；无法计数的提交明确为 UNKNOWN，不能从 after=0 推出恰一次提交。正常验收要求工具每动作尝试次数、响应、读回和业务结果闭合；服务端严格 exactly-once 不在保证内。请求丢响应/延迟提交用例必须证明已转发及实际效果，否则只算“发送不确定”，不算已覆盖晚提交。

### 5.2 执行入口与进程边界

原生执行要求真实 systemd InvocationID、该任务原 service 的 MainPID 和 LoadCredential，依据 [NativeRuntime](../src/vps_kit/traffic/native.py)。从 shell 直接调用 execute、伪造环境变量或用另一临时 unit 启动，不能代替自然执行或账本重入验证。

L3-02 始终由 timer 自然触发。L3-05 的重入负面用例可在批准后的专用实验副本中，待原 service 退出后明确启动**同一生成 service**，取得新的 invocation 后核对零新增 POST；这项故障测试动作不属于本轮授权，也不用于现有 VPS。已有 service 活跃时再次 start 可能只是 systemd 合并请求，应单独记录，不能当作两个执行器竞争锁的证据；跨进程锁竞争由 L2-03 的真实 Linux 两进程完成。注入前后都校验 unit 原文未被添加 wrapper/drop-in。

## 6. 时钟、日历与测试数据

### 6.1 三种时间证据分别登记

1. **真实时间正常链路**：每组合至少一条完整路径使用正常同步时间，构造 UTC 月日历，下一首次边界 B 取当前时间之后约 45–60 分钟的合法整秒。固定周期的原生样例可把该未来 B 作为实验锚点，间隔仍严格为 2592000 秒；这不是修改三台商家锚点。日期为 29–31 时显式选择短月策略。用工具预览和 systemd 计算核对 B；安装/启用的未来授权须严格晚于当时 `now+900s`（整秒样例至少 901 秒），维护区另检查前后业务边界距离至少 900 秒；否则重新规划全新用例，不能临时改 first_boundary 绕过。
2. **离线日历解析**：产品 `traffic calendar` 只有 `--config`，采用当前墙钟，没有 `--now/--base-time`。固定日期对比由待实现的 LAB_ONLY 驱动调用未修改的 `calendar.preview(config, now)` 与 `native.calendar_check(config, now, execute)`，把同一 UTC 基准交给真实 `systemd-analyze calendar --base-time`；不得 mock 后者输出。月日历的多条 OnCalendar 取并集、去重后比较未来 24 次；固定周期分别核对 24 次每日唤醒和未来 24 个业务点，并逐一证明业务点也是日唤醒，远期 first 另核对包含 first 的 24 个业务点。不能把 24 日当作 24 账期。有效日历比对一致，DST 不存在/歧义场景以产品明确拒绝为通过，不能要求 systemd 也拒绝。这是源码函数与系统解析的集成证据；产品 CLI 当前时刻另测，不冒充历史/未来实际触发。[systemd 252 参数说明](https://www.freedesktop.org/software/systemd/man/252/systemd-analyze.html)
3. **整 VM 受控时间链路**：跨月、r2 固定 22 日和真实混合历史，可在独立时间域中设置 guest 初始时间并用实验室 NTP 同步。只在无受测进程、无排队任务且所有相关 timer 已暂停时切换到下一阶段前足够早的时刻；随后必须恢复真实 NTP 同步状态并观察稳定，再按正常速度跨越边界。不得伪造 `NTPSynchronized=yes`、patch NativeClock、使用 LD_PRELOAD 或在正常运行中加速单调钟。此证据标为 `CONTROLLED_VM_CLOCK`，不叫真实商家自然账期。

受控时间用例串行；同一时间源域的其他 DUT 必须停止或暂停相关测试，避免改一个时钟源影响其他用例。证书有效期覆盖所用时间范围。若平台/时间服务无法维持真实同步状态，应标记相应用例 BLOCKED，改用能够满足条件的隔离后端或等待真实日期，不能放宽守卫。

时间提供者分两域登记：正常时间样例使用可追溯实际 UTC 的实验室时间源；受控样例使用**专用 helper VM** 的隔离 NTP，例如 chrony 的隔离网络/local reference 能力。这时 `NTPSynchronized=yes` 只证明 DUT 与实验时间源的系统同步状态，不证明时间源等于实际 UTC，不能混报。具体配置按选定系统软件版本核实；参考 [chrony 隔离网络说明](https://chrony-project.org/doc/4.6/chrony.conf.html)。不修改宿主时钟或宿主 NTP，不让外侧证据收集器进入受控时间域。

G0 必须识别并在受控副本内处理宿主→guest 的时间集成、RTC、guest agent/其他 NTP 竞争源；Hyper-V 确有独立的 VM 时间同步集成，见 [官方说明](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/integration-services)。只调整已登记实验 VM 的集成设置。切换后连续观察至少 60 秒（实验预检值，非 SLA），核对真实同步接口、时间源、单调差分及剩余 ≥900 秒维护窗口。恢复/开机也重新核对；不能假定关掉某个开关即可在所有后端保持偏移。

NTP 负面用例必须观察到执行器下一次 sample 返回真实 `NTPSynchronized=no` 或同步查询失败；停掉时间服务/断 UDP 不保证立即改变此状态。若窗口内未形成目标状态，记录“注入未命中”，而非宣称已测失同步。guest suspend、hypervisor 的**单 VM** pause/resume、关机和 timer 停用分开记录；不休眠共享宿主。guest suspend 能力若缺失则该子场景 BLOCKED，VM pause 不能静默替代。

timer 主动停用后的产品 `resume` 要求未来授权严格晚于 `now+900s`，并通过业务边界维护守卫：B 附近尝试 resume 应拒绝，不能将它与一个始终 active 的 timer 在休眠后恢复混为一谈。漏期后用 `resume --skip-to` 明确授权下一未来边界，零补清零；暂停/关机/恢复测试不通过直接改 first 或手工 enable 来绕过这条规则。若为验证原生 systemd 行为而另设受控系统动作，应与产品生命周期用例分开标记。

专门的时间跳变负面用例才允许在运行中注入偏移；预期停止后续请求并保留已落盘历史。正常路径禁止这种做法。[calendar.py](../src/vps_kit/traffic/calendar.py)规定 240 秒 POST 窗口、900 秒维护间隔；[execution.py](../src/vps_kit/traffic/execution.py)另有 290 秒运行预算、超过 2 秒的墙钟/单调钟偏离保护；service 超时为 300 秒。

### 6.2 合成对象与配额

所有对象在实验面板新建。原生样例 Remark 用含 Unicode 的实验标识；r2/V2.1.2 来源例外，必须使用旧契约的固定 Remark `🇺🇸 LA-Reality`，原 Client Email 必须是对应 `Basic` 或 `Core`。这些公开文本不代表生产身份，UUID、record_id、域名、Token、machine-id 和数据库仍全部来自实验 VM。绑定来自真实 GET，不能照抄仓库 fixture 的 ID。至少有一个其他入口/Client 作旁路哨兵，用于发现越界清零；面板全局和组级合法副作用另按版本记录。

- N=1、2、16 分别覆盖容量；另设 N=3 混合策略场景：一个启用的 stop、一个 quota-recovery、一个双态禁用的 hold。全 hold 为拒绝场景。
- 原生功能样例采用 MiB 级小额度，例如入口 128 MiB、个人 64/8/4 MiB，配置内仍写精确字节；通过实际隔离代理流量达到 8 MiB 个人额度，观察面板自动停用。入口到额另设更小共享池的独立样例。小额度只是便于触发测试，不改变 Basic/Core 生产额度建议。
- 分别覆盖个人不限额 stop、Client 总额大于共享入口、本人未到额但被禁用、入口到额而其他 Client 未到额、配置态/traffic 态不一致、快速增长导致读回无法确认。
- 单独覆盖“本人已经到额后又被人工禁用”：计数不能证明禁用原因。选择 quota-recovery 表示允许满足本人到额条件时恢复；需要保留人工禁用时必须通过维护流程改为 hold，并核对两态禁用。这个歧义是策略边界，不宣称工具能识别操作者意图。
- 降额前依 P2 流程 prepare 并保持 timer 暂停，不能为了造数据在管理事务中偷偷改配额。用于故障构造的离线 DB 修改只能发生在独立停机副本，并标为人工构造；正常到额恢复证明必须用真实流量获得。
- 每层配额均独立核对。入站配额不是单向带宽口径；这里检验面板实际计数/设置与工具契约，不证明商家扣费。

## 9. 故障注入与最多一次请求判定

本节在每个适用组合用独立副本执行；同一失败实例不通过重复 apply/execute“试到成功”。请求窗口内停止其他流量，以便区分计数下降与快速增长；快速增长另设专门用例。

| 故障点 | 触发/观察方式 | 允许结果及禁止事项 |
|---|---|---|
| 已完成暂停、备份未提交、正式文件尚未改变 | 小盘故障或已有文件接口注入；核对暂停完成的证据与 before 原字节 | 保持暂停；仅能按 P3 已知边界撤销意图，不伪称备份完整；若失败发生在暂停前，依第 13 节保留并报告实际状态 |
| 旧 unit 实体移出、mask 尚未建立 | 在明确阶段暂停/中断部署进程并观察磁盘、systemd | 后续执行被阻断；回退仅接受已登记原字节/新字节/明确允许的缺失，不覆盖手工变更 |
| current/Token/新 unit 已替换，日志未完成 | syscall/文件阶段故障及进程中断 | 部署 incomplete/failed 阻断；不能因入口可运行就报告安装完成 |
| pending 尚未持久化或同步失败 | 真实持久化错误、提交阶段观测 | 没有持久意图就不得发送 POST；孤立/临时记录需审查，不自动删掉重试 |
| pending 已持久化，POST 尚未发出 | HTTP 发送前闸门/进程中断，结合文件同步证据 | pending 仍可能代表“尚未发送”；后续照样阻断，不能据请求数为零自动清掉意图 |
| POST 已被真实面板处理，响应丢失或超时 | 网关只转发一次后扣住/丢弃响应，检查 DB 与后续副作用 | 本步骤 pending；即使后来 DB 已提交也不重发；已确认前步骤不回卷 |
| API 响应成功，读回失败或确认落盘失败 | 截断下一 GET、权限/磁盘故障 | 保留不确定记录，不补偿、不再 reset；工具退出码与服务端成功可能不同，分别报告 |
| 所有步骤 confirmed，完成标志未落盘 | 完成提交前故障 | 保留全部 confirmed、整体未完成；禁止重跑清零，按原始证据处理 |
| 运行中时钟跳变/NTP 丢失/耗时跨窗 | 专门负面 VM 的时钟或受控延迟 | 下一次写守卫必须阻断；已发生的写不抹去，停止新增写；不自动延长 240/290/300 秒限制 |

尝试数按 **`(period_id, object, action)`** 计数：每个非 hold Client 的 reset ≤1，入口 reset ≤1，入口 enable ≤1；入口到额恢复时同一入口合法有两种请求，不能按“每对象总共≤1”误判。hold 的 reset/enable 均为 0。正常完成时，令 A 为非 hold Client 数，E 为本周期需要恢复入口时的 1，否则 0，期望 reset/enable POST 总数为 **A+1+E**；失败时按实际到达阶段逐项核对，不能要求所有失败都“零请求”。重入对每种动作的额外 POST 必须为 0。这是客户端请求上界，不等于服务端 exactly-once。

回卷判定也分层：执行中的 `no_unexpected_decrease` 只比较本次连续快照；`check` 与新周期初始读取不提供数据库历史真实性证明。若单独恢复旧 DB 后身份、配额、开关和当前读数仍满足契约，工具可能通过当前检查；不应把这种结果误判为偏离现有实现，也不能据此准许回卷后继续自动化。只有外侧备份/运维记录可证明的回卷，由操作者保持暂停并另行审查。控制日志断链或对象漂移的拒绝用例仍必须通过。

跨月/跨固定周期 pending 的解除只有在证明服务端延迟提交已经结束、确认未来实验账期且证据绑定准确后，才使用既有 `resolve`。service inactive 或停止客户端不能单独证明面板队列已清空；观察能力不足时保持 BLOCKED。若原始控制日志损坏/孤立，不在普通 resolve 能力内。

这是隔离来源样例，1 GiB=1024³ 字节。来源若另有合法多 Client 配额，则逐项原样保留，不在接管时替换为上表推荐值。固定旧 unit 名及旧锁是全机资源，两个套餐用例不能在同一活动 VM 上并存。

### 10.2 正向用例顺序

1. **r2 首次前**：在独立干净 VM 安装已识别 r2，首账期在未来，无应有而缺失的周期。生成本机候选并接管；证据必须如实为“尚未发生首账期”，不能生成成功 ledger。
2. **r2 完成后**：启用的旧 timer 自然跨过实验时钟的固定边界，真实 API 产生 schema 2 completed；完成旧账期联合核对，再在 ≥900 秒维护间隔外接管下一合法边界。
3. **真实混合历史**：在另一个副本，用已识别 V2.1.2 和官方 3.7.0、合成对象，设置原 `first_cycle=M−1` 并完成该旧周期，避免人为留下更早应有而缺失的账期。固定 Remark/Email 依第 6.2 节；原两层额度必须为 Basic 500 GiB / Core 1000 GiB。只需少量非零真实流量，不必耗尽额度。封存 schema 1 和原配置。
4. 旧 `manage.py` 必须在 **M−1 月 22 日自然完成超过 15 分钟之后、该月结束之前**执行 backup/install；此时 r2 候选 `first_cycle=M`，状态中 M 月尚不存在。暂停旧 timer、先备份，再独立修改实验面板为 r2 配额并核对，最后安装，得到真实 manifest：`old_cycle=M−1`、`status=installed`、全部 `state_before` 摘要及原对象绑定。backup/install 间不跨月，已启用对象须低于新额度；若时间切到 M 月才运行，旧工具会拒绝，不能改断言绕过。这是旧工具在实验室的来源建立过程，**不属于 0.4.0a2 接管，也不将改额步骤混入 0.4.0a2 迁移**。
5. r2 自然完成 M 月，获得 schema 2；在 M 月边界后且距下一授权边界严格大于 900 秒时接管。保持 schema 1 原字节和 manifest。0.4.0a2 候选 `schedule.first_boundary_utc` 必须仍等于 **r2 的 M 月首次边界**；M+1 只是导入后 `next_boundary_utc` 的未来授权，不能把候选 first 改成 M+1。使用原 V2.1.2 config/manifest 的明确引用，核对原对象绑定、`state_before`、first_cycle 和所有历史。每个 OS、Basic/Core 都执行，不用合成 confirmed 替代真实生成链。
6. 0.4.0a2 接管后核对旧 runner 拒绝执行、旧 unit 磁盘与生效 mask、双锁、原历史摘要、新 timer 唯一性；迁移自身零 POST。等待下一实验边界，由 0.4.0a2 自然执行，再核对旧账本未改且只有一个新授权周期。

legacy marker 可作为明确标记的合成格式样例验证配对、时间顺序及删除阻断；若没有已识别旧程序的真实生成证据，不把合成 marker 当真实清零证明。验证“删除整个 marker 对”时，必须在旧 backup **之前**放入合法且成对的更早月份 marker，让真实 manifest 的 `state_before` 登记两者，再从独立副本删除。原本没有 marker 的来源是合法正向分支；不能删不存在的文件就声称验证了阻断。混合历史主链至少包含真实 schema 1、真实 r2 安装 manifest 和真实 schema 2。负面副本另改绑定/old_cycle、丢失旧配置、插入 pending/未来记录/未知文件、混用套餐，均应拒绝接管。

原 r2 runner 不支持 3.10.2；M02/M04/M06 只验证该来源版本失配被拒绝，之后如需原生 0.4.0a2 正常链路，使用无旧残留的独立副本，而非删除迁移证据继续安装。

### 10.3 回 r2 的两种观察点

两种正向回 r2 用例均从**最近一次非 rollback 部署操作仍为 migrate**的独立副本开始，P2 配置修订未变、owner 未移除、服务/排队请求已终止且维护窗口满足。执行历史可以增加；后续 upgrade/credential 则会改变最近部署操作。不能先轮换/升级，再要求 `deployment-rollback` 跨过最近操作直接回 r2；本版本无多级自动回退。升级和凭据回退在各自独立分支验收，旧操作 ID 作为拒绝用例。

- 0.4.0a2 尚未产生任何流量请求时，回退原文件后旧 timer 仍暂停，不自动恢复旧自动化。
- 0.4.0a2 已产生 pending 或 confirmed 时，再做回退：新 control/ledger、旧状态、计数均保留；只恢复 manifest 登记的程序/配置/unit；`r2_resume=NOT_AUTHORIZED`。

两种情况都不能通过运行旧备份 runner 来“验证恢复”，否则会绕过新历史门槛。回退恢复原 runner 后，退役脚本的拒绝能力已不再存在；旧 r2 不理解新历史，手工启动旧入口或重新启用旧 timer 可能绕过保护。因此这里只验收恢复文件身份、暂停状态和历史保留，不能把回退后的旧入口描述为技术上仍禁止执行，更不能让它再次清零。

## 11. 每个自然边界的联合验收

现有 `audit` 只能证明结构并给出当前系统快照，`check` 只能证明当前条件；二者不独立完成自然账期验收。由实验室采集器在 B 前、service 结束后，以及受控观察期末采集：

1. **调度/进程**：B 的 UTC 和实验时区表示、该业务点对应 InvocationID/MainPID、起止、Result/退出码及其 journal。月日历记录下一月边界；固定周期分开记录下一日唤醒、严格未来业务点和账本当前授权（可能漏期在过去）。LAST/LastTrigger 和 service 最近属性会被普通日醒覆盖，须在 B 当时关联 invocation 并封存，不能用后来一次普通日成功验收旧业务期。
2. **持久历史**：产生时 revision/config/program/object 绑定、period_id、边界、每步骤 not_sent/pending/confirmed/not_required、前后快照和 completed。正常路径应完整；故障路径按第 9 节验收，不强行要求 completed。
3. **请求/数据库**：按周期/对象/动作记录尝试数、面板已知处理/提交数及未知项，关联 API 与 SQLite 一致性快照；不把前后归零当作服务器提交计数。SQLite WAL 场景使用一致性备份/只读事务，不只复制主数据库文件。原始 DB 和 Token 只在受保护实验存储中，不进公开仓库。
4. **对象/业务**：实际 Client 和入口状态、配额、当前用量、旁路哨兵、Xray 内部重启与连接事件；停止故障/恢复可用后，实验客户端重新连接并完成带校验值的上传/下载。建议记录 B 前及服务结束后各 60 秒连接事件；此时长是观察窗口，不是 SLA。
5. **连续性**：重入无新增 POST、旧记录原字节未改，下一授权/period 正确；固定周期完成后 audit 应推导下一授权为 B+30；B+1 日零 API、控制 head 不变，仅 B+30 自然执行时才新建下一期执行 ledger 并发送该期动作。未决或漏期跨天/跨期仍阻断，不能用未来预览掩盖过去授权。缺失证据返回 REVIEW_REQUIRED。

正常低延迟样例应在 `[B, B+240s)` 内完成所需写请求，并在 service 的 300 秒预算内结束。1 秒 timer 精度不是硬实时 SLA；实际启动晚于窗口应安全阻断并判该正常样例未通过。当前计数可因新流量非零，入口和 Client 不要求相等；不能通过验收时再清零取得零值。

## 12. 现有 CLI 的复用方式

所有路径和 UUID 均取 G0 登记的**实验 VM**。以下命令是确认后的接口模板，本轮只作静态解析，不在 VM 或宿主执行系统动作。文件名只是计划约定，不代表文件已经生成；`<…>` 必须替换。正常运行从已校验的 0.4.0a2 解包目录开始，安装后再用稳定入口。

## 13. 停止、回退和环境退出

| 情况 | 首要动作 | 恢复边界与通过条件 |
|---|---|---|
| 身份/网络白名单不符 | 不开始写操作，隔离该测试任务 | G0 重新核对；不能尝试连接某台现有 VPS 证实身份 |
| 计划/GET 前置失败，尚无写入 | 保留实际原 timer/文件状态，记录失败 | 不报告“已暂停”；修正输入须形成新的显式测试步骤，不自动 retry |
| 部署中断/failed | 停止继续应用，采集日志/文件/备份和实际进程状态 | 只评估最近非 rollback 操作的有界 deployment-rollback；孤立/损坏日志、旧目录、备份、配置、时间条件不符则阻断，不反复调用 |
| P2 prepared 取消 | 在暂停状态下将实验面板恢复原配置，再核对 cancel 前置条件 | cancel 不清零，保持暂停；P3 rollback 不是 P2 半安装修复器 |
| 执行 pending/服务端结果未知 | 停止新增测试触发，保留账本；等待并观察该实验面板队列 | 不重发、不删记录、不提前 resolve；无法证明延迟提交结束则保持 BLOCKED |
| 正常程序/凭据回退 | 只恢复登记文件并做现有验证 | 自动化暂停、历史/计数不回卷；旧凭据撤销则失败，不能冒充认证恢复 |
| 回 r2 / VMRack 月脚本 | 先通过来源、完整目标与备份的前后两次核对，按最近迁移恢复原文件 | 新旧 timer 暂停，保留全部新旧历史；返回 `legacy_resume=NOT_AUTHORIZED`，r2 另有同义字段；恢复旧 runner 后不再具有 stub 的拒绝能力，禁止以再次执行验证恢复 |
| 部分退役或来源/锁漂移 | 按 R1/R3/R4 记录精确停止点；已暂停则保留暂停，未暂停则如实保留原状态 | 部分退役的恢复同时避开新旧业务窗口；完全退役通过守卫后仅检查新业务窗口；未知字节/源集合/锁身份不通过时不覆盖，不现场删证据或换锁重试 |
| 日志损坏、不可恢复文件系统或无法证明来源 | 从控制台封存/关闭该 disposable VM，保留证据 | 从干净检查点创建**新的测试 run**；原 run 仍 FAIL/BLOCKED，不用快照覆盖失败证据后报 PASS |
| 测试正常结束 | 按白名单暂停实验 timer，确认服务/排队任务与故障工具退出，撤销实验 Token | 证据导出并核验后方可关闭/删除已批准的实验副本；不触及宿主和生产任务 |

产品守卫可能因 failed 状态拒绝普通 pause。实验室紧急停止可通过虚拟机控制台，对登记的精确 timer 禁用并确认状态；这是实验室处置，不称为产品 pause 通过，也不使用通配符。正在运行的进程先在服务时间预算内观察；超时后只对已确认的测试 PID/VM 执行预先批准的中断或断电，并按不确定状态封存。

整 VM 检查点用于测试隔离和重新开始，不是产品回退功能。恢复快照必须换 run_id，导出旧证据并核对没有两个相同身份实例同时活动；不能从恢复快照后的成功推导原中断事务已修复。旧锁文件不主动删除，boot 内 inode 不重建；数据库/ledger/marker 不通过回退清理。

### 16.3 普通日、自然边界及漏期（L3-13）

每个六组合各有一条真实当前时间的固定周期首期正常链路，锚点 B 可按第 6.1 节设为未来约 45–60 分钟；三组历史商家锚点和跨多个 30 天用例在独立受控时间域完成，标记 `CONTROLLED_VM_CLOCK`。二者均不缩短间隔，不 patch 产品时间源。每阶段提前完成暂停和时间域准备，真实 NTP 稳定后以正常速度跨界。

| 子场景 | 操作顺序与证据 | 通过标准 / 失败处置 |
|---|---|---|
| F30-01 首次前日醒 | 首次设为 A 的后续合法网格点；在 first 前一个普通日保持 timer 已启用，让它自然触发；保存前后 head、计数、GET/POST 尝试和 invocation | `BEFORE_FIRST_BOUNDARY`，面板 GET=POST=0，control head/旧源状态不变；本地守卫及 systemd 凭据/runtime/journal 活动不计为业务零写入 |

F30-03/05 明确独立区分完成、漏期、未决。已完成期在其 `[B,B+240s)` 内重入可为 `ALREADY_COMPLETED`；此后且下一授权未到时为 `NOT_DUE`，均零新增请求；下一获授权期到来后必须允许正常新期执行。完成后的下一授权由历史立即推导，不等于提前新建下一期执行 ledger。

每个普通日醒的“head/字节不变、零 API”区间，从本阶段 pause/时间准备/resume 全部完成、timer waiting 且 service/Job 静止后开始，到该次 invocation 结束及只读采集结束为止。前一准备阶段可能合法追加 maintenance/transition，保留并单独核对；不得拿准备前 head 与日醒后 head 要求相等。API 计数归属于该 invocation 及其子进程；采集器如额外调用 check/discover，其 GET 单独登记，不能混入执行器零请求指标或用采集器请求冒充执行器动作。

### 16.4 配额恢复与修改（L3-14/15）

固定周期按 L3-03 重做 N=1、2、16 和 N=3 混合策略，完整保留每个 Client 的 record_id/UUID/Email/个人额度/策略：本人到额且获准的 quota-recovery 才可恢复；父池满不替代本人条件；hold 两态禁用且零个人重置，入口后续操作不能误启用它；stop 双态启用、可不限额。正常到额由隔离代理真实产生；同时记录入口 reset 后仍禁用、最终单独 enable 的正确顺序。

每个规则修改用独立 P2 事务：保存旧授权 → revision+1 plan → prepare 暂停 → 如有额度变化才改实验面板 → apply 全量 GET → 显式选择恢复。monthly→fixed、fixed→monthly、固定换锚点均要求新生效边界不早于旧授权；仅展示时区变化不改 first/当前授权。新增/删除/改 Email 通过完整 Client 集合核对；中途手工编辑或降额不满足前置时拒绝。cancel 只处理尚未安装的 prepared，failed 不交给 P3 rollback 冒充通用修复。

专门在距业务边界数日、但距普通日醒不足 900 秒时做维护：无 service/Job且锁可得时可以通过；另让日醒与管理竞争，应因进程/Job/锁阻断而非“日醒维护禁区”。失败保持实际暂停阶段，不杀 service 或绕过双锁重试。

### 17.3 M2 隔离与同事务首期再确认（L3-17）

M2 只解决不能精确归属的已关闭历史；服务端还可能提交、未知入口未关闭、进程/Job 活跃均拒绝，不靠等待一周期解除。操作者明确接受可能延长一周期以上及到额后暂不可用，迁移不改变额度解决等待。

1. 正常分支：evidence 的 mode=M2、quarantine_accepted=true、actions=[]、last_boundary_utc/no_resets_after_actions=null；取得可信 closure 证据。计划 first 选网格上不早于预计 cutover+2592000 且满足未来维护距离的边界；apply 后用实际 cutover 复核。
2. 实际 cutover 取“退役完成、旧进程/队列结束、服务端副作用关闭”最晚时间。若 first 仍合格，提交来源/授权并保持 paused；记录实际时间和 first，不用 plan 生成时间替代。
3. 延迟分支用已审核无真实写入的退役阶段闸门：在旧 units/stub/cron 全部退役且守卫通过后，保持管理进程等待，墙钟和单调钟以正常速度一起前进。可用 35 刀算例：plan 在 `2026-10-10T01:30:00Z`、预计 cutover=`01:49:00Z`，原 first=`2026-11-09T01:50:00Z`；实际退役资格采样延到 `2026-10-10T01:51:00Z`，最低网格应为 `2026-12-09T01:50:00Z`。闸门必须位于完整退役后，不能在旧入口仍可执行时跨旧月日危险区。这个分支不靠运行中跳钟/伪造采样制造成功；时间能力不足则 BLOCKED。
4. 期望 `WAITING_CANDIDATE_RECONFIRMATION`：原 plan 不覆盖、同 operation_id 的部署记录追加 candidate/candidate_sha256/actual cutover；旧入口仍 retired，新 timer 未安装或暂停，control 无首次运行授权，POST=0。
5. 操作者核对新 first、候选差异仅 first 后，按同 operation_id、输出 candidate_sha256、**原已确认包**调用 deployment-reconfirm。确认记录追加，安装及全量 GET 后仍 paused。对实际确认时 now 再检查 first 资格；一次新候选不会被程序无限自动顺延。
6. 独立反例分别传错 operation/hash、改对象/额度/锚点/Token、换包、追加 control、来源漂移、first 已过期、failed 阶段重新 apply/reconfirm。应拒绝，不给新授权；等候阶段的 precondition 拒绝不等于 failed 可重试，实际阶段以部署日志为准。不用换 task UUID/删日志重建接管。
7. 等候阶段另走拒绝新 first 的文件回退：最近操作仍为该 vmrack-migrate，原证据及备份完整，通过 R3/R4 后只恢复登记文件；新旧自动化暂停，`legacy_resume=NOT_AUTHORIZED`。不再运行恢复后的旧 runner。
8. 隔离期间任何手工清零、DB 恢复、旧入口重新出现或未知延迟副作用都会使证据资格失效：由实验记录识别后暂停、审查；不自动刷新 cutover 继续。普通日服务成功不证明隔离未被外部破坏。

通过标准：实际 cutover 下界、完整候选及确认链可复核，first 不提前；未再确认零运行授权；首次只在批准后的自然实验边界执行一次。失败/不确定则封存相应 run，不能靠手动清零或删记录结束隔离。

### 17.4 持续退役与按阶段回退（L2-14/15、L3-18/19，R1/R3/R4）

完成接管后，在普通日醒、业务写入前及每个适用写管理入口分别注入 stub、实际 mask、登记旧 config/Token/marker、旧状态文件集合增删、受保护备份、旧目录删除、活跃/排队和锁身份漂移；专用 cron/新增 cron 与配置目录精确集合按 VMRack 分支验收。

集合判据按来源分别定义：VMRack 配置目录必须恰为 `{reset.conf, api-token}`，旧状态顶层须为普通文件且文件集合与登记一致；VMISS 持续守卫核对登记 source_images（包括其配置/Token）及旧状态树中文件/符号链接集合，不把未登记的合法历史配置旁件（如旧 reset.conf）或集合定义以外的空目录泛化为必须拒绝。新增未知状态文件/删除登记状态文件、登记配置/Token 内容变化仍须拒绝。首次来源收集的目录限制另按 collect_r2/collect_vmrack 验证，不用首次收集规则推定持续守卫检查了目录全集。每次独立副本，保存前后全部登记目标、source_images/source_backup、control/deployment head、两个锁的 dev/inode、invocation 和请求数。旧目录删除不能取消已提交来源、旧锁或守卫。

| 阶段 / 分支 | 回退步骤及期望 | 通过标准 / 退出 |
|---|---|---|
| plan 未应用 | 只读比较旧状态，结束该候选 | 没有正式文件或调度变化，无需文件恢复；候选不授予清零资格 |
| backup 未提交 | 最近日志显示未获完整备份；核对正式目标必须仍为原字节 | 仅既有无备份退出契约允许时撤销意图；不能恢复未知文件或假称 backup 完整 |
| partial 退役 | 保留失败后状态，在新旧业务维护区外复核完整目标及不可变来源；按最近 manifest 文件回退 | R4 的旧 900 秒窗口生效；旧 runner/cron 尚可执行时不得绕过；零新增 POST |
| fully-retired / 等候再确认 | 核对 stub/mask/专用 cron、无进程/Job、备份及原证明；在新业务维护区外调用 rollback | 不重新引入错误旧月日维护禁区；恢复文件、两侧 timer 暂停，来源状态返回 returned；新 control/历史/计数不恢复 |
| migrate 后有 pending/confirmed | 先关闭晚副作用，按最近迁移和配置资格文件退出，保留未决链 | 回退不清空 pending、不授权重置，不运行旧文件；后续重新接管须另行评审 |
| 接管后 upgrade / credential | 只可回退最近对应操作；暂停前/后都通过完整 retired 守卫 | 不跨过最近操作直接回源；旧 runner 不再 stub 等漂移须在正式恢复前拒绝；旧 Token 已撤销不等于授权恢复 |
| 仅缺 `/root/` 原证明 | 先测试运行守卫使用受保护 source_backup 可通过，再在独立文件退出分支检验原件条件 | 初始迁移退出应在暂停/正式恢复前拒绝；不自动从 backup 重建原件。运行不依赖原件不等于文件回退可缺原件 |

正式回退会恢复旧可执行 runner，stub 的技术拒绝能力随之不再存在；只验收原文件身份、暂停和历史保留，不能通过再次执行旧 runner 来证明安全。未知文件变化、损坏/孤立日志或坏备份保持 BLOCKED；通过控制台封存该副本，用新 run 恢复干净环境，不把 VM 快照当产品回退修复。

### 17.5 程序格式升级与退出（L2-09）

两个真实旧包分别独立安装为 paused，记录原事件/活动配置/授权，再由 0.4.0a2 已校验解包 CLI 生成 upgrade plan 并 apply；不伪造版本号造样本，不顺便修改月日历/商家/Client 配额。

- `0.3.0a2 → 0.4.0a2`：保留原 v1 配置和事件，追加能力 format 转换及 program 身份；月日历不会自动变固定周期。旧源码须拒绝新 config/v2、format/vmrack_import/deployment_v2 能力，拒绝通过不等于旧版能运行新历史。
- `0.4.0a1 → 0.4.0a2`：同格式正常更新 program，既有格式记录不增加/重写，稳定 task/period/配置保持。独立兼容文件回退只恢复登记旧版本且 paused；a1 已知问题不再通过真实写请求重演。

- 无论版本，后续配置修订、owner 退役、不是最近部署操作、坏旧目录/备份或退役来源漂移均阻断；兼容回退也不删除控制历史或未决意图。程序回退与恢复真实 API 权限、计数或业务状态分别取证。

## 18. 0.4.0a2 五项修复的强制回归用例

本节以 [E1-2](vmrack-review-20261025.md) 的 R1～R5 为追踪 ID，分解为每组合适用子场景；初始结果全部 NOT_RUN。所有破坏性注入只在获准的 disposable 实验副本；正常规则“不得删除持有锁/未知覆盖/改 unit”与专门负面注入分开记录。没有命中证明不能以某个拒绝退出码填 PASS。L1 测试仅提供反例定位，不能复制其结果替代 L2/L3。

### 18.1 R1：下一写入前复核持有锁（L2-03/14、L3-04/19）

**前置与步骤：** 原生六组合必测；VMISS/VMRack 来源分支在三种 OS 的 3.7.0 已接管副本必测。用真实 Linux 两进程/fcntl 先证明新→旧锁顺序、第二锁忙时释放第一锁。自然执行的第一 Client durable pending 落盘后，分别替换/删除新锁或旧锁；必须先使进程停在下一次目标身份检查**之前**，再注入并释放闸门，保存 held fd/路径 dev/inode、同步完成、检查和发送尝试顺序。

R1 闸门逐分支登记：NativeRuntime 的慢 verify 返回后、末尾 check_lock_identities 之前；BudgetPanel.send 的 fence.check 之后、check_lock_identities 之前；Journal._atomic/DeploymentFiles.write/link 的 before_replace 回调或其后身份检查入口之前；NativeSystem/NativeDeploymentBackend._run 在身份检查之前。直接原版 CLI 可用有命中证据的进程/函数或 syscall 观察来定位，但不能把真实 rename/exec syscall 入口误作身份检查之前。使用既有 fault/execute 依赖驱动时，必须标明函数/接口集成证据，不能借另一 service 或 wrapper 绕过原 InvocationID/MainPID 取得原版执行通过。

API 网关收到请求、execute 依赖内部已经开始命令，或身份检查已完成才替换路径，都晚于本分支目标检查；此类结果标记检查后非原子竞争边界/未命中，既不能用下一写发生判 R1 失败，也不能以先被其他守卫拒绝判 R1 通过。0.4.0a2 没有把路径身份检查与后续 syscall/HTTP 封装成原子操作；本用例不扩大这一保证。无故障基准和有效注入分支均须记录准确先后，锁故障前不发测试 POST。执行路径的闸门须在剩余 240 秒写窗、290 秒执行预算及 300 秒 service 超时内释放；若先超窗、失同步或被超时中断，只记录该保护或设施未命中，不能据此填 R1 通过或判产品身份检查失败。该预算不套用于 R2 独立只读函数的跨日等待。

**通过标准：** 路径替换/删除报 `LOCK_REPLACED`；相应分支的下一 POST=0、正式发布或管理写=0；已提交的 pending 必须保留，后续日醒/业务期重入不得重发。未形成 pending 的发布/管理分支保留原 head/已提交状态及不确定 stage/孤立证据，按实际完整性守卫阻断，不补造 pending。无故障对应正向通过；原生、VMISS 和 VMRack 没有分支漏检。临时 stage 文件如在发布前已建立，按原事务不确定残留处理，不据“正式写=0”宣称文件系统完全零变化。

**证据与回退：** 记录确切触发位置及 fault 前后 control/deployment head、正式目标、进程与两把锁。故障后不在原 run 换回新 inode、删 stage/意图再重试；封存，待进程退出后对登记 VM 做有界停止/关闭，必要时新 run 恢复干净检查点。生产锁从未纳入注入范围。L1 对照：`test_vmrack_review.py::LockReviewTests`。

### 18.2 R2：日醒临界重采样不能放宽有效契约（L2-12）

**前置与步骤：** 六组合固定周期、独立原生副本，timer enabled/active/waiting；first/当前下一授权严格晚于整个试验预计结束（含第三采样等待或推进至次日）的时刻至少 901 秒，并证明全部跨越的日醒均不是可执行授权业务点。优先取远期锚点/first 的新任务，不能只检查第一次日醒附近，也不在试验中修改 first 绕过。用 LAB_ONLY 驱动调用未修改 `NativeSystem.verify()`，真实读取原 unit/systemctl、真实 systemd-analyze；在校验期间自然跨一次日醒，留足正常运行预算。基准应只发生一次重采样、两份 unit 再读取。精确第二快照的注入，可在既有 execute 依赖的闸门中延迟调用、由外侧在独立副本改变真实 guest 配置后再读取；不得伪造 show/calendar 输出或给原 service 加 wrapper/drop-in 后冒充原版正常链路。

逐项独立命中：timer/service 原文件字节；FragmentPath/LoadState、DropInPaths、NeedDaemonReload；Persistent、AccuracyUSec、RandomizedDelayUSec、Triggers；Type、Restart、RemainAfterExit、TimeoutStartUSec、RuntimeDirectoryPreserve；任一侧 Job、timer disabled/非 waiting。只测原字节拦截不等于已测第二快照 effective 属性：属性注入须在第二轮字节读取之后、实际 show 之前命中。实际属性取值以该 OS 的 show 为准，无法构造则对应项 BLOCKED，不 mock 通过。

另让第三采样点越过再次日醒：可以只读驱动在独立副本等待到次日，或专门负面时间域在闸门间注入 guest 时钟推进并明确标记 `CONTROLLED_VM_CLOCK_NEGATIVE`；后者只证明再次跨日拒绝分支，不代替正常自然单次重采样。不得缩短固定周期或伪造 NTP；此只读函数用例不是启动自然执行 service。

**通过标准：** 干净的一次推进可通过；任一字节/有效属性/Job 漂移被相应 unit 守卫拒绝，不能仅以 next 时间相同通过；第三采样确实再次跨日须命中 `SYSTEMD_DAILY_WAKE_CHANGED_AGAIN`；若先被其他时间守卫拒绝，只记录额外保护证据，该目标分支仍为 BLOCKED/未命中，不能代填 R2 通过。面板请求=0；验证过程不发布配置、不启用或重试。原版 CLI 的正常路径另在 L3-13 保留。

**证据与回退：** 两轮文件/属性、采样时间、真实命令计数和 gate 时点闭合；停止故障设施，保留实际状态，不在同一失败 run 修 override 后改成 PASS。由控制台按登记 VM 封存/退出；只读调用无业务历史回滚。L1 对照：`DailyResampleReviewTests`。

### 18.3 R3：正式恢复前核对来源和完整目标（L3-08/19）

**前置与步骤：** M01/M03/M05，VMISS 和 VMRack 各自已完成迁移、最近操作仍是迁移的副本；另有迁移后 upgrade/credential 副本。分别在 rollback 调用前修改登记旧 config/Token、marker、原 `/root/` 证明及旧状态文件集合；VMRack 另测配置目录项增删，VMISS 的合法未登记配置旁件不列为必须拒绝；以及在 pause/quiescent 后、正式恢复前闸门修改旧 runner、VMRack 登记 cron、旧 unit、新入口。每次只改变一个已登记对象，记录其外部注入值；不能把注入本身算成回退程序写入。

迁移后的 upgrade/credential 回退，另将旧 runner 改成非 stub、破坏 mask/cron/backup/状态集合；验证完整 retired 守卫仍生效。原 `/root/` 证明缺失的独立副本先证明运行期使用受保护备份可通过，再验证**初始迁移文件退出**仍要求原件。VMISS 原件为历史配置/manifest 时按各自 plan 登记核对，不把 VMRack 证明字段强加给 VMISS。

**通过标准：** 暂停前漂移必须在暂停/恢复/新回退日志意图前拒绝；control/deployment head 和未注入正式目标均不变。暂停后漂移可以已暂停，但在恢复任一正式目标前拒绝，head 不追加回退意图，除外部注入外正式目标未变。不覆盖未知字节，stub/mask 只因明确故障注入而变；升级/凭据路径不能绕过来源守卫。缺原件不能自动从 backup 还原证明。

**证据与回退：** 对所有 plan.before/source_images/source_backup 建清单，比较故障前、注入后、拒绝后三份状态，保留语义 head 和 POST=0；不能只看最终 error code。拒绝后保持实际暂停阶段并封存；未知来源不满足通用 rollback，不反复调用。无故障正向恢复身份/暂停/历史保留另测。L1 对照：`RollbackReviewTests`。

### 18.4 R4：部分退役的旧 900 秒窗口（L3-19）
