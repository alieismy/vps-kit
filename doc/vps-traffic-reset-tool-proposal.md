# VPS 流量重置管理工具方案

> 所属项目：`vps-kit` · 首个工具：`traffic`  
> 文档版本：0.1.1 · 日期：2026-10-24（Asia/Singapore）  
> 状态：**方案草案，待用户确认后开发**。本文规定拟实现的能力和验证要求，不代表工具已经实现、发布或部署。  
> 本轮授权：编写本地方案，核对公开源码与既有材料；不连接或修改 VPS，不清零，不调整生产 timer/service，不初始化或推送 Git 仓库。

## 1. 结论、范围与决策状态

推荐保留仓库名 **vps-kit**，采用单仓库、统一命令入口、工具按职责分目录的结构。第一个工具提供 `vps-kit traffic` 交互向导和子命令，复用 V2.2.0 r2 的执行与保护思路，移除 VMISS、Basic/Core、固定 Remark 和固定账期的代码绑定。

用户通过面板地址、API Token、入口选择、期望配额、月重置日、时刻和时区配置自动重置；程序负责发现对象、校验状态、预览调度、管理配置与 timer、核查执行证据。基础设施使用者无需手工编辑 systemd 文件或为每台主机复制专用脚本。

本工具重置的是 **3X-UI 计数**，不操作服务商账单。它不改变 Xray 流量计量方式，也不证明服务商额度与面板读数具有固定比例。

| D-09 | 原创工具代码拟采用 MIT，最终许可证由仓库所有者确认 | 不复制未明确许可的上游实现；第三方许可清单是公开发布门槛 |

批准本文表示同意按这些边界进入开发，不等于批准接管任何现有 VPS。若希望首版直接修改面板额度或支持多个入口，应先修订 D-02/D-03 和对应验证范围。

## 4. 目标支持矩阵与运行条件

### 4.1 平台

| 操作系统 | 设计采用的 Python 系列 | 面板 3.7.0 | 面板 3.10.2 | 优先级 |
|---|---|---|---|---|
| Debian 13 | 3.13 | 待隔离验证 | 待隔离验证 | 主平台 |
| Debian 12 | 3.11 | 待隔离验证 | 待隔离验证 | 支持平台 |
| Ubuntu 24.04 LTS | 3.12 | 待隔离验证 | 待隔离验证 | 支持平台 |

Python 系列依据 [Debian 12 包资料](https://packages.debian.org/bookworm/python3)、[Debian 13 包资料](https://packages.debian.org/trixie/python3)和 [Ubuntu 24.04 发布说明](https://discourse.ubuntu.com/t/ubuntu-24-04-lts-noble-numbat-release-notes/39890/1)。不锁死安全更新小版本；安装时检查实际能力。

目标依赖为 Python 3.11+、作为 PID 1 的 systemd、curl、tzdata、CA 证书和标准文件权限/锁能力。unit 采用 systemd 252 可用的功能子集，使用前执行本机解析校验；不为统一环境自动更换 Python、systemd 或关闭系统安全策略。[systemd 252 timer](https://www.freedesktop.org/software/systemd/man/252/systemd.timer.html)、[systemd 252 execution](https://www.freedesktop.org/software/systemd/man/252/systemd.exec.html)

不支持将 Windows、WSL 或普通无 systemd 容器当作生产运行环境。Windows 可以做编辑与纯逻辑模拟；容器可测试 HTTP/数据库，但不能替代真实 PID 1、重启、文件系统与凭据传递验收。缺依赖时报告缺项，由操作者决定安装，不静默执行系统升级。

### 4.2 面板和拓扑

首版要求原版 3X-UI、一个本地面板、一个受管本地 VLESS 入口；每个 Client 只关联该入口。其他未受管入口可以存在，但不得与受管 Client 共享身份；若启用整机预算校验，必须另行计入其他业务，不能重复分配整机额度。

对象绑定必须同时核对入口内嵌 Client 集合与 Client 详情返回的关联入口集合；不能用 traffic 记录中的单一 `inboundId` 替代关联关系。每个 Client 的关联集合必须恰好是目标入口，UUID、记录 ID 和 Email 分别唯一且互相对应；发现跨入口关联时整项任务拒绝写入。按 Email 调用的重置会处理该记录关联的入口，遗漏关联校验会扩大重置范围。[3.7.0 Client 重置路径](https://github.com/MHSanaei/3x-ui/blob/v3.7.0/internal/web/service/client_traffic.go)、[3.10.2 Client 重置路径](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/service/client_traffic.go)

远程节点、全局流量推送、定制计量构建、跨入口共享 Client、其他协议、Docker 化面板和非 systemd 安装均不纳入首版写入支持。发现或无法排除影响计量的拓扑时标记待核对，不以“入口 nodeId 为空”单独证明完整本地拓扑。配置来源核对属于接管前提，具体可自动采集的证据在详细设计中与版本适配层固定。

版本通过本机官方程序读取并与用户选择交叉核对；同名定制构建仍需安装来源证明。升级面板不会自动扩大适配范围，未验证版本可显示本地状态但不能启用重置写入。

## 5. 候选方案与工具集结构

### 5.1 候选比较

| 方案 | 操作成本 | 可靠性与复用 | 维护/发布成本 | 结论 |
|---|---|---|---|---|
| 保留专用脚本和手册 | 新主机与每次改配置仍需多步骤人工核对 | 当前限定配置经验可保留 | 初期最低，长期重复材料较多 | 作为迁移前基线保留 |
| Bash 向导＋重写重置逻辑 | 输入简单 | JSON、版本差异和状态恢复须重新实现 | 初期快，后期测试与维护负担较大 | 不推荐作为完整核心 |
| Python 统一 CLI＋复用 r2 核心规则＋systemd | 一套入口完成管理 | 可保留状态机并增加通用生命周期 | 中等改造量，无新增常驻服务 | **推荐，设计可行性置信度高** |
| Go 单二进制重写 | 安装形态简洁 | 需重新证明执行与恢复行为 | 增加编译发布与双实现对照成本 | 当前收益不足，暂不采用 |

风险主要集中在版本适配、配置变更与历史连续性，不在菜单界面。当前不估算未经拆解的工期或人天；第 18 节用可验证里程碑约束投入和继续条件。

## 6. 参数与配置模型

### 6.1 用户输入

| 参数 | 必填/默认 | 校验与用途 |
|---|---|---|
| 面板 URL | 首次必填，可读取已存配置 | 明确 scheme、host、port、base path；允许空根路径；禁止 URL 内凭据、查询串和片段 |
| API Token | 首次必填，隐藏输入或从受保护文件读取 | 由版本适配层验证格式；不作为命令行明文参数，不写到普通配置或计划文件 |
| 入口 Remark | 输入或列表选择 | UTF-8 精确显示；存在重复时按 ID、端口等进一步选择，不自行取第一条 |
| Inbound Total Flow（界面 GB） | 默认读取；可输入期望值 | 按已验证的面板单位换算成整数字节；必须大于 0；不自动写面板 |
| 月重置日 | 1—31 或 `last` | 29—31 必须明确短月规则；`last` 表示每月最后一天 |
| 重置时刻 | `HH:MM:SS`，必须确认 | 可将省略秒显示规范化为 `:00` 后确认；不能隐式使用午夜 |
| 时区 | 必填 IANA 名称或 UTC | 如 America/Toronto；不接受 CST 等含糊缩写，不改变 VPS 系统时区 |
| 首次生效边界 | 自动建议未来边界，用户确认 | 新建和修改都不补跑过去边界，迁移另受旧记录限制 |
| Client 范围 | 自动列出目标入口全部现有 Client，逐项确认 | 精确集合覆盖，包括 hold；至少一个非 hold Client；每项保存稳定身份、Email、期望配额、策略；不静默纳入新 Client |
| 到额恢复策略 | 新建默认 stop；迁移保留原策略 | 见第 8 节；明确显示是否可能在自然账期恢复启用 |
| 商家额度/单位 | 可选；开启预算核查时必填 | 商家 GB=10⁹、GiB=1024³，不能凭面板标签推断商家单位 |
| 预算模型/预留 | 可选；预算核查时显式确认 | 首版提供“用户自定面板额度”和“普通代理双向计费估算×2”；未知模型不计算安全额度 |

面板表单标作 GB，既有基线按 1024³ 字节处理；两个适配层必须用表单/接口及隔离样例分别验证，精确整数或可无损换算的十进制字符串进入配置，不用浮点近似、不把 bool 当作整数。[3.7.0 换算实现](https://github.com/MHSanaei/3x-ui/blob/v3.7.0/frontend/src/utils/index.ts)、[3.10.2 换算实现](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/frontend/src/utils/index.ts)

### 6.2 自动发现与绑定

程序自动发现 OS、Python、systemd、时钟同步、面板版本、unit 位置、入口监听/端口/协议、Client 列表及当前计数、既有 reset unit、已知旧版文件与状态。machine-id 仅在本机用于绑定，脱敏输出不展示原值。

首次选择入口后生成不可因重命名而变化的任务 ID，保存主机/面板、入口 ID、监听/端口/协议、Client 记录 ID/UUID 指纹。Remark、Email 仍需核对，但不能作为唯一对象键。重新创建任务、改变显示名称、改 Remark 不得获得新的计费身份或空历史。

每个面板入口只允许一个重置所有者；首版每台只允许一个受管任务。全局注册记录用于发现同对象重复计划，不能只依赖 timer 文件名。旧工具使用不同文件名时也必须先接管或证明不冲突。自定义脚本是否存在需操作者补充确认，自动扫描不声称能发现一切外部清零行为。

### 6.3 配置结构与变更

逻辑字段分为：`schema_version`、稳定任务身份、面板/传输配置、对象绑定、期望配额、Client 策略、月日历、首次允许边界、可选商家预算、兼容适配标识，以及配置修订号。新 schema 与 legacy schema 2 分开命名，不能覆盖旧记录使其看似原生新格式。

运行参数与 Token 分离。旧配置修订不可变，历史账本引用当时的修订；Token 轮换只改变凭据引用，不重新生成账期身份。调度或配额变更产生新修订，记录 old→new 的生效边界，不用新配置摘要重新解释旧账本。

配置入口拒绝重复 JSON 键、未知字段、非法类型、越界额度、重复 Client、无受管 Client、路径穿越和换行注入。所有外部命令采用固定可执行文件与参数数组；Remark、Email、URL 不得拼进 shell、unit 名或任意 systemd 指令。

候选保存生成时的配置修订、绑定、unit/程序摘要和历史指纹；apply 在维护锁内重新比较，不能把一份过期候选覆盖到已被其他会话修改的部署。并发正常增长的流量不要求等值，但必须重新通过额度与策略门槛。配置、unit、入口指向切换用持久化 manifest 记录阶段，重进时识别半安装并保持写入阻断，不把多文件替换假定为一个原子事务。

## 7. 交互流程与命令职责

下表为拟议接口，不是已经可执行的命令。动作名在详细设计时固定；不提供生产重置命令样例。

| 接口 | 用户得到什么 | 允许的副作用 |
|---|---|---|
| `vps-kit traffic` | 菜单：新建、修改、状态、核查、账期验收、暂停/恢复、导入、回退 | 进入菜单本身不改变状态 |
| `traffic discover` | 环境、入口、Client、已有任务的脱敏列表 | 本地读取＋有界 GET |
| `traffic plan` | 生成候选及差异、未来边界、预计操作范围 | 默认只展示；显式保存时只写受保护候选 |
| `traffic apply` | 应用已核对候选 | 本机配置/unit/备份/维护记录；不清零、不修改面板配额 |
| `traffic edit` | 在现有修订上生成修改计划 | 默认不直接覆盖生效配置 |
| `traffic status` | 本地配置和调度状态 | 不读 Token，不发 API，不写受管状态 |
| `traffic check` | 当前对象、额度、策略、时钟与运行条件核对 | 只读 GET；不试探重置权限 |
| `traffic audit` | 指定边界或最近已到期账期的执行证据 | 严格只读，不自动修复 |
| `traffic resolve plan/apply` | 核对未决历史并授权指定未来边界继续运行 | plan 只读；apply 仅追加人工处置记录，不改原账本、不补发旧请求 |
| `traffic pause` / `traffic resume` | 暂停或恢复未来调度 | 仅目标 timer；resume 必须通过运行门槛，不手动启动 service |
| `traffic migrate plan/apply` | 原 r2 的接管预览与有界执行 | 先只读；apply 才暂停旧调度、备份、导入 |
| `traffic rollback` | 程序/配置回退和剩余限制 | 保留历史与计数；默认保持调度暂停 |
| `traffic credentials rotate` | 替换本机凭据引用并检查读取权限 | 仅凭据与维护记录；不改周期、不清零 |
| `traffic remove` | 退出自动化 | 禁用并移除受管 unit/程序引用；默认保留受保护历史与备份 |

单次新建向导顺序：环境检查 → 面板连接 → 入口选择 → Client/额度/策略确认 → 月日历和首次边界预览 → 冲突检查 → 展示完整变更摘要 → 一次确认保存或安装。最终选择明确为“仅保存候选”“安装并保持暂停”“安装并启用未来计划”，不重复询问已确认字段。

读操作不能隐式安装依赖、修复权限、刷新配置、创建缓存/锁/账本、生成 pyc 或自动暂停 timer。报告默认标准输出；另存报告是显式动作。系统日志/API 服务自身可能记录访问，不属于本工具写账本的承诺范围。

非交互模式需要显式目标和候选摘要，不能用一个全局 `--yes` 绕过身份、历史、近边界或未决状态检查。交互与非交互均不回显 Token；中断输入不留下半写入正式配置。

## 8. 多 Client 配额与恢复策略

### 8.1 配额语义

入口限制该入口总使用量；Client 限制自身使用量，不能把两个层级相加当成额外消耗。多个 Client 的配额之和允许小于、等于或大于入口配额；大于表示共享总池下的个人上限，不表示每人保证获得完整个人额度。

示例均为合成配置，不表示目标主机当前状态：

| 模式 | 入口 GiB | Client A | Client B | 含义 |
|---|---:|---:|---:|---|
| 分配份额 | 250 | 150 | 100 | 个人上限分别控制，整体仍受 250 限制 |
| 共享总池 | 250 | 250 | 250 | 两人合计最多受入口 250 约束 |
| 只限制入口 | 250 | 0 | 0 | Client 不限额，不能对其采用 quota-recovery |

商家预算独立于面板额度。例如明确采用二进制单位、双向估算×2、零预留时，500 GiB 商家额度可配置入口 250 GiB，1000 GiB 可配置入口 500 GiB；这是用户选择的预算模型，不能推广为所有服务商和所有拓扑的精确计量关系。

### 8.2 首版改额边界

工具可以导入、展示、比较并保存各 Client 的期望配额。默认保留面板现值；若输入不同目标值，产生“面板操作待完成”清单，停止正式配置应用。已有受管任务必须先按已授权维护计划暂停目标 timer、核对 service/queued job 并保存变更前备份，随后才提示操作者手工改额；改后只读核对通过，才能应用对应候选。全新任务尚无调度时不需要虚构暂停步骤。修改重置计划不隐式改配额，配额降低也不提前清零。

手工改额后取消或安装失败，保持实际已确认的暂停状态；工具不会自动改回面板，也不能直接恢复仍期望旧配额的 runner。恢复旧自动化前必须由操作者将面板与旧期望值重新对齐并核查，或者完成新候选应用。迁移 r2 时禁止同时改额，见第 13 节。

启用或接管时要求活跃对象的当前用量低于新有限额度；若已经超过，明确提示降低额度可能影响代理使用，不能宣称无中断迁移。当前处于自然到额停用的任务按既有策略核查，不与新建/迁移可用性门槛混为一谈。

`updateTraffic` 在所查 3.10.2 controller 中更新 upload/download，**不是修改限额的接口**。首版禁止使用它，也禁止取一份 GET 后的完整对象再把旧 up/down 回写以改额。自动改额若后续纳入，应独立验证专用字段更新、并发计数增长和失败恢复。[3.10.2 controller](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/controller/client.go)

### 8.3 策略

| 对象/策略 | 允许的自然边界行为 | 阻断情形 |
|---|---|---|
| Client stop | 已启用时重置并核对仍启用 | 任何相关启用状态不符 |
| Client quota-recovery | 已启用正常处理；禁用且本人有限额度已耗尽时允许重置及核验恢复 | 禁用但未到额、无限额、身份/字段漂移 |
| Client hold | 工具不主动改变开关和计数，不发该 Client 重置请求 | 实际仍启用或策略记录不一致 |
| Inbound stop | 已启用时重置入口 | 入口禁用 |
| Inbound quota-recovery | 已启用时正常重置；已耗尽且禁用时，在非 hold Client 与入口清零确认后恢复入口 | 禁用但未到额，或任一步不确定 |

上述“Client 启用”分为配置态和 traffic 态：内嵌 `enable` 必须与独立 Client 记录一致；traffic.enable 单独核对，不能强制它始终与配置态相同。stop 要求两态均为 true；quota-recovery 在有限额度耗尽时允许任一态为 false，成功读回须两态均为 true；hold 要求两态均为 false，不因历史用量已到额而自动恢复。quota-recovery 不允许无限额，即使当前启用也不能配置该策略。任何一个 Client 不符合对应条件，必须在首个 POST 前阻断整个账期。

入口到额不等于各 Client 本人到额；不能据入口已满而恢复所有被禁用 Client。入口是否需 setEnable 依据入口自己的初始状态及耗尽证据决定。hold 保证工具不主动改变其开关或清零其计数，不把已有连接产生的自然计数变化误认成工具重置。两种面板版本的 Client 重置都可能附带恢复启用；这是一次受条件约束的恢复尝试，不能承诺一定恢复成功，也不能为恢复失败追加第二次 resetTraffic。

API 不可靠提供禁用原因；人为关闭已耗尽对象也可能符合 quota-recovery。向导必须解释并取得该策略授权；持久停用 Client 应改为 hold，持久停用入口应暂停调度并使用 stop。策略变更属于显式配置更新，不依据现场开关悄悄改写。

所有非 hold Client 共用入口自然账期，逐个记录；首版不支持每个 Client 独立日期或时区。新增/删除/重建/改名 Client 都需新候选与身份核对，不能运行时发现就自动纳入。hold Client 保留计数后，入口与所有 Client 累计值可能不一致，这是策略结果，不应自动修复。

## 9. 月日历与 timer 生命周期

### 9.1 日历规则

配置保存月日规则、`HH:MM:SS`、IANA 时区及首次允许边界，使用同一日历模块供 runner、timer 生成、预览和 audit 使用。

29—31 日要求选择 `skip`（短月无该日则不执行）或 `clamp-last-day`（短月采用月末）；不默认猜测服务商行为。`last` 始终为月末。应通过有限的 OnCalendar 表达式覆盖短月规则，不靠每日轮询清零，也不让 runner 每月重新安装 timer。重复表达式对应同一边界时须归一化；生成结果与本机 `systemd-analyze calendar` 至少未来 24 次及跨闰年测试相符。[systemd 252 日历规则](https://www.freedesktop.org/software/systemd/man/252/systemd.time.html)

时区不能改成全年固定 UTC 偏移。遇到夏令时不存在/重复的本地时刻，首版拒绝该候选并要求提供服务商确认的规则；未得到规则不自动平移或执行两次。每次生成计划和边界执行前均检查；预览显示服务商时区、UTC 和使用者选择的显示时区。

### 9.2 unit 设计原则

timer 使用日历触发、`Persistent=false`、`AccuracySec=1s`、`RandomizedDelaySec=0`；service 为 `Type=oneshot`、`RemainAfterExit=no`、`Restart=no`、`TimeoutStartSec=300s`，采用边界后 `[0,240)` 秒新写请求窗口。运行目录使用 `RuntimeDirectoryPreserve=yes` 保留稳定锁，不能随单次 service 结束删除；重启主机后按已登记路径安全重建运行目录，持久历史不能存放在 /run。timer 只允许生成的 OnCalendar，不添加 OnBoot/OnActive/时钟变化触发或其他隐含清零入口；只为 timer 建立启用关系。秒级配置不等于硬实时保证，已经 active 的 service 不会因 timer 再次触发而产生独立实例。[systemd timer](https://www.freedesktop.org/software/systemd/man/252/systemd.timer.html)、[运行目录生命周期](https://www.freedesktop.org/software/systemd/man/252/systemd.exec.html)

`Persistent=false` 仅关闭重新激活 timer 时的持久补跑，不能替代 runner 时间门槛。系统休眠、排队或时钟校正后仍须校验自然边界；每个 POST 前重新核对同步状态、单调时钟与墙上时间差、配置修订和剩余预算，超窗不发新请求。新 unit 只排序依赖并检查 x-ui 正在运行，不通过 Requires/自动启动来拉起已被人工停用的面板；不直接照抄 r2 的依赖声明。

采用稳定任务 ID 生成 `vps-kit-traffic-<id>.timer/service`，Remark 不进入文件名。完整生成并解析自己的 unit，不任意接受未知 drop-in；发现外部覆盖时报告差异，不覆盖用户设置。必须验证生效 FragmentPath、NeedDaemonReload、Job、下一触发和实际策略，不只比较磁盘文本。

### 9.3 创建

创建流程为：只读发现 → 候选预览 → 冲突和未来边界检查 → 经确认安装程序/配置/unit → 解析校验与 daemon reload → 本地及 API 只读验收 → 按用户最终选择保持暂停或启用未来 timer。

启用时再次确认目标边界仍在未来、没有 service/queued job、没有当前未决步骤。安装/启用不调用重置端点，不以手动启动 service 测试效果。接近任一旧/新调度边界不足 15 分钟时不进行安装/维护，不能只计算新计划以避开旧 timer 即将触发的时刻。

首次允许清零边界可能晚于普通月日历的下一次唤醒。首版允许 timer 提前唤醒执行器，但执行器必须在调用 API 和创建账期账本前返回 `BEFORE_FIRST_BOUNDARY`；不能以新月份文件存在代替授权。预览和 status 分别显示“systemd 下一次唤醒”和“首次允许清零”，不把两者强制报成相同时间；测试覆盖推迟多个周期的首次生效。

### 9.4 修改

修改先生成差异，展示旧计划、新计划、旧边界是否已执行及下一允许边界。应用时取得维护互斥，暂停目标 timer，确认 disabled/inactive、service 已结束且无 queued job，再创建已验证备份、安装新修订与 unit、核对生效状态。

原状态为暂停时保持暂停；原状态为启用时，变更计划必须明确是否恢复。只在原确认范围、所有验证通过且未来边界仍成立时恢复 timer。暂停前的只读失败保持原状态；暂停命令失败或状态不可读时报告实际状态/未知，禁止继续安装，不能声称已暂停。只有已验证 disabled/inactive 之后的应用失败才要求保持暂停，不自动恢复旧调度。不能通过停 timer 强杀正在写入的 service；无法确认已结束时停止维护。

修改日期/时区不能被当作“新任务”，也不能仅按 YYYY-MM 是否不同判定新账期。普通切换先核对旧规则最近应执行边界及完成/跳过依据，并计算提交时仍有效的旧计划下一允许清零边界 B_old（包含原首次允许边界和历史处置约束，不是单纯的 timer 下一次唤醒）；新规则首次可执行边界 B_new 必须不早于 B_old、严格晚于最后已完成边界，并满足未来窗口。两个边界均转为 UTC 比较，迁移和跨时区不重置此门槛。

例如合成场景中旧规则每月 22 日、10 月 22 日已完成，10 月 23 日改为每月 1 日：新规则的 11 月 1 日仍早于旧下一边界 11 月 22 日，普通切换最早为 12 月 1 日。计划须明示取消的旧触发、延长的计量区间及可能到额停用；操作者可以取消变更继续旧计划，不能无提示拉长区间。特殊短账期需独立依据并先修订设计，不作为首版绕过按钮。

切换成功后登记旧未来边界被替代，旧计划不再执行；同一 UTC 边界重合只保留一次授权。只改配额、Token 或显示信息不改变原已授权边界。计划修改、remove 后重建、URL/Remark 改名和 hold/stop 切换均沿用对象历史，不能通过新配置摘要获得新的清零机会。

### 9.5 暂停、恢复与移除

pause 只停止自动重置调度，保持代理开关原状；已运行的写请求不会被宣称取消。resume 只允许未来边界，不补跑暂停期间错过的周期。remove 默认保留历史与备份、移除目标自动化入口；不删除面板对象、Token 的上游授权或计数。清理凭据和保留材料是单独明确的退出选择。

## 10. 核查、审计和输出

### 10.1 三类只读结果

| 层级 | 核对内容 | 不能推出的结论 |
|---|---|---|
| 配置检查 | schema、修订、绑定、权限、unit 和日历一致 | timer 已启用或 API 可写 |
| 运行条件检查 | NTP、面板版本、GET 契约、配额、启用策略、冲突与未决历史 | 下一次一定执行成功 |
| 账期验收 | LastTrigger、service 起止/退出、账本、唯一确认日志、API 与证据连续性 | 服务商已换期或代理实际可用 |

status 默认只读本地，显示 `未到期/已暂停/就绪/未决/失败/已完成待业务确认` 等状态。check 可以调用允许的 GET；权限信息无法从只读证据确认时，明确要求人工确认所用 Token 的 admin scope，不发送探测性 POST。audit 支持显式边界和最近已到期边界，不能把本月日历标签直接当作实际已到期周期。

返回结构化 JSON 或人类可读文本。最低字段包括任务/配置版本、目标边界、调度状态、下次时间、证据分项、当前可用性、请求次数、是否有写操作、错误码及下一步。错误码稳定，说明中文；日志输出字段白名单，不打印原始响应或凭据。

### 10.2 通过与异常

历史验收要求全部受管步骤有可信 confirmed/not_required、完成时间合法、同边界没有重复写入证据、服务与日志相互一致。当前计数可以非零，入口与 Client 可以不相等；账本记录重置前后证据，不能通过再次清零制造通过结果。

审计较早账期时，systemd 的 LastTrigger 和当前 service 起止属性可能已属于后续执行，不能强制它们等于被审计的历史边界。应使用该边界的不可变账本和对应时间段日志/执行标识核对历史，另行展示当前调度；历史日志缺失则降低证据等级，不用最近一次属性冒充旧账期证据。

验收至少区分 `PASS`、`NOT_DUE`、`REVIEW_REQUIRED`。较晚核对发现再次到额停用时，历史完成与当前不可用分别报告。日志轮转、元数据缺失、低计数快速增长等属于证据不足，不能自动断言重置失败。

默认无自动重试、无自动修复。只读代码路径禁止调用生产 runner 的写入口，关闭 pyc、缓存及受管目录创建；并发变更导致证据不稳定时返回待复核，不通过拿写锁、修复文件来获得“只读通过”。人工业务核查仍包括服务商时间、代理实际请求及是否存在其他手动清零。

## 11. 防重复清零、执行顺序与持久状态

### 11.1 不变量

- I-01：同一稳定对象与已授权自然边界，已完成步骤不自动重发；完成记录不重写完成时间。
- I-02：发送任何 POST 前，意图必须先可靠落盘；落盘失败则不发送。
- I-03：POST 超时、响应丢失、读回失败、字段漂移或确认落盘失败，均可能表示效果不确定，不自动重试。
- I-04：未决和来源不连续的历史不能因跨月、改配置、换任务名或迁移而失去阻断作用。
- I-05：创建、修改、核查、暂停、恢复和回退都不清零。
- I-06：人工删除状态、整机快照回卷及服务端无幂等键，超出严格 exactly-once 保证；工具必须说明边界。

### 11.2 执行流程

自然触发后：取得稳定执行锁 → 校验主机/配置修订/调度所有权/历史 → 核对时间与全部对象 → 按稳定 Client 顺序重置非 hold Client → 重置一次入口 → 必要时启用入口 → 最终读回 → 保存首次完成证据。

每步使用 `not_sent → pending → confirmed`，无需处理为 `not_required`。pending 文件与目录同步成功后才 POST；读回核验身份、配额、计数变化和阶段预期启用状态后才 confirmed。借鉴 r2，但不能把旧单 Client `stop` 候选的“所有对象始终启用”检查直接套到允许入口到额恢复的流程：入口初始禁用时，在最终 setEnable 前应按显式阶段预期核对。

首次 POST 前检查全部 Client，之后每次写入前后重新核对目标及全局身份/Client 集合、配置修订、未决状态和阶段预期。已确认 Client 又被后台禁用、出现未知 Client 或入口开关漂移时停止，不临时重分类并再次恢复。每个 not_required 必须有原因和证据：Client 仅允许因 hold 跳过，入口 enable 仅允许因初始已启用跳过；不得把失败、超时或权限不足记作 not_required。

Client 清零与入口清零不构成跨对象事务；部分成功不可通过补偿清零或回填旧计数回滚。首版遇到当前账期 pending 或部分完成后退出，不自动继续剩余步骤，即使时间窗仍有效。

### 11.3 状态模型

分开保存任务注册、不可变配置修订、调度切换记录、每次自然边界的账本、维护/迁移清单和历史人工处置记录。账本绑定稳定任务/对象、UTC 边界及本地时间规则、配置修订、步骤和前后快照。自然边界 UTC 不是唯一防重复依据，还须检查同对象已授权周期与切换历史，防止修改日期产生第二次“新边界”。

文件更新采用同文件系统临时文件、严格权限、原子替换、文件与目录同步。runner 与 apply/edit/resolve/rotate/rollback/remove 等写管理操作使用同一稳定执行锁，锁文件不会在运行中删除或被新路径替代。只读操作不创建或持有此写锁。无法取得锁、写入失败或时钟异常即停止；测试应覆盖替换前后及目录同步失败，而非只覆盖函数返回值。

正常已完成历史可跨月保留，不阻止合法未来账期。历史 pending、部分完成、绑定变化或来源异常应被分类；解除未来阻断需要独立、不可变的人工处置记录，绑定原始文件哈希、对象、证据、未来允许边界和责任人。此记录不改写旧步骤、不把 pending 改为成功，也不授权重放旧请求。当前未决请求不能仅凭一份处置文件立即再次发送。

pending 表示“请求可能已经发出”，包含落盘后、真正发送前崩溃的情况；仅凭 pending 不能判断服务端是否执行。HTTP 错误、success=false 也可能发生在部分副作用之后，不能归类为可安全重发。即使全部单步已 confirmed，但最终快照/完成记录未成功落盘，也属于待审计，不能自动重新执行。允许未来运行的处置必须覆盖服务端延迟提交是否仍可能发生、业务周期对齐及最早未来边界；单纯等待超时、service 已退出或计数很小都不是解除依据。

这里的“阻断”是执行器拒绝新的写请求，不表示 timer 自动变成 disabled/inactive。timer 可能仍会在未来唤醒执行器，由历史检查再次拒绝写入；status/check 必须分别显示调度开关和历史阻断。暂停 timer 由明确的管理动作完成，账期失败不会被报告成已暂停成功。

### 11.4 失败语义与调用预算

连接超时初始取 3 秒、单请求总时限 10 秒、HTTP 自动重试为 0；生产写入无重试。全部 Client 预检为 `1+2N` 个基础 GET，具体 discovery/audit 的辅助调用单独计数，不能固定声称总是 3 次。

正常清零写请求上界为非 hold Client 数 M 加一次入口清零，再加可选一次入口启用；额外写调用不在白名单。完整 GET 预算由适配层与读回策略在详细设计固定并测试，不能直接复制旧候选的 18 GET 或单 Client 数字。

16 Client 是配置上限，不保证慢接口都能在 300 秒内完成。启用前显示只读耗时，边界执行达到预算即停并保留状态。服务端排队请求可能在本机退出后落库；不能把 service inactive 或 curl 超时等同于请求取消。[3.10.2 流量写队列](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/service/traffic_writer.go)

## 12. 3X-UI 版本适配与 API 边界

| 项目 | v3.7.0 | v3.10.2 | 本工具要求 |
|---|---|---|---|
| Client 重置与启用顺序 | 先尝试启用，再清零 | 先清零，再尝试启用 | 使用版本专属副作用模型；两者均需 GET 确认恢复 |
| resetWeekday | 不设该字段必填要求 | 独立 Client/traffic 要求整数 0 | 不能把 null、bool、字符串或非零值解释为默认 |
| reset/resetDay/expiryTime | 要求关闭续期/到期 | 保留要求，并检查新增周期字段 | trafficReset=never；阻止面板内部与外部重复重置 |
| 内嵌旧 JSON 缺字段 | 保留已验证的 resetDay/trafficReset 缺键兼容 | resetWeekday 缺键需实际隔离迁移证据 | 在证据形成前拒绝写入，不以 3.7.0 经验自动放宽 |
| 写响应与副作用 | 成功响应不等于恢复已生效 | 同样，且需核对节点/全局计量影响 | 每步读回，业务可用单独验收 |
| Inbound 重置 | 服务层清 up/down；controller 成功后设置 Xray 待重启 | 同样 | 不清 Client、不隐式启用 Inbound；不承诺无 Xray 重启影响 |

顺序差异依据 [3.7.0 Client 实现](https://github.com/MHSanaei/3x-ui/blob/v3.7.0/internal/web/service/client_traffic.go)与 [3.10.2 Client 实现](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/service/client_traffic.go)。`resetWeekday=0` 关闭每周续期，而 `resetMax=0` 表示不限制次数，不能混用；历史 resetCount 不必为零。[3.10.2 流量字段](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/xray/client_traffic.go)

`resetDay` 是自动续期的月日；`trafficResetDay` 是定期流量重置的月日，不能混用。两层 trafficReset 均为 never、Client reset/resetDay 为 0、3.10.2 resetWeekday 为 0、两层 expiryTime 为 0 才符合本工具调度前提。trafficReset=never 时残留的合法 trafficResetDay（例如默认 1）不是仍启用定时重置的证据，不要求改成 0。resetMax/resetCount 是次数元数据，不替代关闭周期字段；缺键兼容只适用于已明确验证的内嵌表示，不推广到独立 Client/traffic 权威字段。[3.10.2 模型](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/database/model/model.go)、[定期重置任务](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/job/periodic_traffic_reset_job.go)

Client 重置和 Inbound 重置作用不同：前者调整目标 Client 计数及相关组统计基线/时间元数据，并可能恢复 Client；后者清入口计数，不代替逐 Client 清零，也不代替入口 setEnable。两个版本的 Inbound controller 成功后均调用 SetToNeedRestart，后台再处理待重启标记；Client 恢复路径也可能产生重启需求。必须把可能的 Xray 重启、连接扰动和异步读回变化写进最终动作预览及隔离验收，不能将“不发送 systemctl restart”解释成“API 无重启副作用”。[3.7.0 Inbound controller](https://github.com/MHSanaei/3x-ui/blob/v3.7.0/internal/web/controller/inbound.go)、[3.10.2 Inbound controller](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/controller/inbound.go)、[3.10.2 后台处理](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/web.go)

版本适配层只开放所需端点：入口列表、目标 Client 详情/流量，以及逐 Client resetTraffic、经绑定的入口 resetTraffic、策略允许的入口 setEnable。拒绝 resetAll、批量清零、updateTraffic、对象删除、节点更新与任意用户指定 URL 路径。Client Email 必须编码为一个路径段，不允许改变端点结构。[3.7.0 Client 路由](https://github.com/MHSanaei/3x-ui/blob/v3.7.0/internal/web/controller/client.go)、[3.10.2 Client 路由](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/controller/client.go)、[3.10.2 Inbound 路由](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/controller/inbound.go)

固定业务端点契约如下；`{email}`/`{id}` 只来自已核对绑定，所有路径追加到明确的 panel base URL，不能在这些参数中输入任意路径：

| 方法与相对路径 | 目标 / 契约 |
|---|---|
| GET `/panel/api/inbounds/list` | 发现及核对目标入口、全部内嵌 Client；多个候选须明确选择 |
| GET `/panel/api/clients/get/{email}` | 核对独立 Client 记录和完整 inboundIds 关联集合 |
| GET `/panel/api/clients/traffic/{email}` | 核对该 Client 当前计数、限额与 traffic.enable |
| POST `/panel/api/clients/resetTraffic/{email}` | 仅自然边界中经策略允许的单个 Client；不带任意更新对象 |
| POST `/panel/api/inbounds/{id}/resetTraffic` | 每个已授权边界至多一次入口计数清零 |
| POST `/panel/api/inbounds/setEnable/{id}` | 仅入口恢复步骤，固定 enable=true；不扩展为 Client 或其他入口的开关操作 |

字段来源也必须分清，不能把不同 JSON 表示要求成完全相同：

| 表示 | 配额与身份 | 周期与状态要求 |
|---|---|---|
| Inbound 列表的目标入口 | total、入口 ID、listen/port/protocol/nodeId 与绑定一致 | enable 按入口策略；trafficReset=never、expiryTime=0 |
| settings 内嵌 Client | totalGB 与各自期望值一致，id 对应 UUID，集合精确匹配 | enable 与独立 Client 一致；reset/expiryTime=0；缺 resetDay/trafficReset 仅用既有明确兼容规则；3.10.2 resetWeekday 缺键仍受迁移证据门槛限制 |
| Client 详情的 client | totalGB、记录 id、uuid、email 与绑定一致；inboundIds 恰好一个目标 | reset/resetDay/expiryTime=0、trafficReset=never；3.10.2 resetWeekday=0 |
| Client traffic | total 与期望值一致，email 精确匹配，up/down 为非负整数 | reset/resetDay/expiryTime=0；3.10.2 resetWeekday=0；enable 按双态策略；不要求该响应拥有 trafficReset/trafficResetDay |

两层计数不要求相等。显式 null、bool、字符串数字或非零值不能走“缺键兼容”；解析器保留缺失与零的区别，不能用通用 get-default 覆盖未知情况。声明的 GET 白名单不包含写入探测，admin scope 无法从读取成功推出。

路径统一基于显式 panel base URL，不能因为 route 名相同就宣称两个版本完整兼容。HTTP 200 还需 success=true、响应类型与对象字段通过。没有原子条件更新或服务端幂等请求键的证据，不承诺消除所有前置 GET 到 POST 的人工编辑竞态。

3.10.2 存在主面板推送的全局计数叠加路径；API 数值不一定等于本机原始统计。首版不以 API 数值回填数据库，接管前须确认符合本地计量范围。[3.10.2 全局计数实现](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/service/inbound_traffic_global.go)

## 13. 现有 V2.2.0 r2 的接管迁移

### 13.1 支持入口与禁止事项

首版自动迁移仅接收当前安装为已识别哈希的 r2、当前配置合法 schema 2、本机身份和已知 unit/状态目录；不以“文件名像旧脚本”判断版本。当前仍安装 V2.1.2、未知改版、配置 schema 1 或旧 3.10.2 单主机候选时，只出只读报告，不套用 r2 自动迁移。

此限制不排除 r2 部署保留的更早 schema 1 账本和 legacy 标记。它们必须作为历史单独导入：schema 2 记录按产生时的 r2 配置验证；schema 1 记录按对应旧配置、已验证旧格式及迁移 manifest 验证，不能拿当前 r2 配置摘要验证所有旧账本。现有 r2 迁移备份只有 runner/config/service/timer 四类文件及状态指纹，不能声称其中包含 Token 或完整账本备份。缺少旧配置/来源证据时保留原字节，阻断有疑义的接管，不补造成功状态。读取历史采用专门解析器，不执行备份中的任意脚本。

迁移不更新面板、不修改配额、不升级 OS 或 Xray，不同时变更账期、Client 集合和恢复策略。第一阶段保持已批准业务配置，只改变管理工具归属；以后再通过 edit 独立修改。

### 13.2 两种可接管时点

| 原部署状态 | 迁移判断 |
|---|---|
| r2 首次允许边界尚未来到，当前没有 r2 执行证据 | 可以计划未来接管，但必须核对更早 legacy 历史、首次边界及无未决请求；不能伪造首次完成记录 |
| 已完成一个或多个 r2 自然边界 | 只读验收最近应执行边界并检查历史，再接管下一合法边界 |
| pending、部分完成、最近边界应执行却无可解释证据、异常来源 | 阻断 apply；先审计，不以重新安装解决 |
| 目标面板已不同于旧 runner 支持版本 | 先评估旧调度是否失配及面板迁移证据，不能套用普通热接管 |

### 13.3 接管阶段与恢复点

1. **只读盘点：**配置、已安装程序/单位、权限、旧状态、调度及对象指纹；生成迁移计划，不暂停旧 timer。
2. **维护门槛：**用户确认后暂停旧 timer，确认 disabled/inactive、service 已结束、无 queued job，远离旧/新边界并取得共享锁。存在不确定服务端请求时停止，单靠等待固定秒数不能证明结束。
3. **备份：**保存经哈希核验的原程序/配置/unit/凭据恢复引用与 manifest；记录旧调度状态。原始账本与旧标记保留，可制作证据副本但不提供覆盖回滚入口。
4. **历史导入：**按旧 schema 独立验证，登记原路径、原字节哈希及语义映射；保持完成、未决、缺失等分类，不把所有记录压成“上次成功”。记录接管前后的唯一调度所有者。
5. **安装与退役：**新配置/unit 先保持暂停；备份确认后归档旧 unit 实体，并在原 timer/service 名建立 mask，原 runner 路径改为只报“已迁移、拒绝执行”的退役入口。完整原文件保留在受保护备份中。完成文件、生效 unit、旧入口退役、API、身份与历史连续性核对。
6. **启用选择：**按已确认的迁移计划启用未来新 timer 或保持暂停。再次核对旧 timer/service 为 masked/inactive、旧 runner 退役、新 timer 唯一及下一边界；不启动 reset service。
7. **自然验收：**未来边界后使用通用 audit，分别核对服务、账本、日志及代理/商家状态。

共享锁必须具体兼容旧部署：旧 r2 使用 `/run/vmiss-traffic-reset/reset.lock`，新工具不能只锁自己的目录。接管和保留 r2 回退能力期间，新 runner 与所有写管理操作均按固定顺序持有新任务锁及旧锁，从最后状态复核一直覆盖到提交或退出；保留旧锁路径/文件身份，不删除重建正在使用的锁。旧 r2 不认识新锁，但会与同一旧锁互斥。无法取得任一锁时停止，不能等待至跨入边界后继续；只读计划不获取这些写锁。

锁只防并发，不防旧 r2 在新工具退出后顺序执行；旧 r2 又不读取新账本，因此退役入口是启用新 timer 的必要条件。disable 只是过渡，不能充当退役成功。已安装在 /etc/systemd/system 的 unit 实体需先按 manifest 备份归档，再建立 mask，不能假定直接 mask 一定覆盖现有文件。mask 阻止原 unit 名的通常启动；退役入口阻止按旧路径手工调用 runner。回退才允许按原字节恢复，不能在普通 resume 中解除保护。[systemd mask 语义](https://www.freedesktop.org/software/systemd/man/252/systemctl.html)

迁移导入保留原首次允许边界和已经完成的周期，不能因为安装发生在某月就把 first_cycle 改为该月。先停旧、后启新，并分别检查磁盘和 systemd 生效状态；任一时刻至多一个可执行调度所有者，暂停阶段允许零个，成功启用后才要求恰好一个。普通 r2 接管仅适用于其已支持且现场符合契约的 3.7.0；当前面板已经为 3.10.2 时，工具即使支持该版本，也必须先有单独的升级/历史衔接证据，不能跳过旧部署版本失配问题。

安装中断用 manifest 记录阶段，包括旧 unit 归档、mask 和 runner 退役；再次进入先恢复或审计，不重复创建备份后覆盖原恢复点。新工具 preflight 和执行前验证退役文件摘要及生效 mask，保护不完整则阻断。root 显式解除 mask、替换退役入口或执行备份中的旧脚本属于绕过管理边界，不能声称工具可以阻止这种操作；向导不提供这样的清零入口。

## 14. 回退、凭据恢复和退出

| 场景 | 允许恢复的对象 | 必须保留 / 默认状态 |
|---|---|---|
| 新工具安装失败，且尚无新 POST 意图或未决请求 | manifest 对应的程序、配置、unit | 保留原历史；两侧调度保持暂停，验证后再决定恢复旧 timer |
| 新工具已有 POST 意图或执行记录 | 可恢复程序文件，原新历史继续保留 | 首版回旧 r2 始终保持暂停，不将最新账本替换成旧副本或反向伪造旧账本 |
| Token 更新失败 | 受保护的旧凭据引用，且旧凭据仍有效 | 不回滚周期、不重发请求；外部已撤销凭据不能靠文件回退恢复 |
| 面板被升级/回退或数据库从快照恢复 | 本工具只做状态审计 | 不恢复 3X-UI 数据库，不用旧计数填充当前计数，暂停写入直至账期对齐可解释 |
| 用户退出工具 | 禁用自己的 timer，移除明确归属的入口 | 不动代理对象/计数；历史保留与凭据清理由明确选择决定 |

r2 不会读取新工具的调度切换和历史处置记录，因此“旧程序启动成功”不能算完整回退。首版 rollback 不提供把新账本反向转换成 r2 账本的能力：自接管后只要存在新 POST 意图、已执行步骤或相关历史处置，回到旧 r2 一律保持调度暂停；不以当前计数、恢复旧配置或跳过一个月份证明安全。只有能证明接管后没有任何新重置/恢复请求、没有未决状态、旧配置和面板仍匹配且旧下一边界仍合法时，才可另行评审恢复旧调度。结果分别显示 **程序已恢复，自动化未恢复** 或经独立核查后的未来调度状态，不自动启用旧 timer。

任何回退都先通过维护门槛，验证备份主机/对象/哈希/版本，拒绝未知文件覆盖。manifest 与备份不是计数回滚授权；不删除 pending、不改 first_cycle、不恢复旧整机快照来获得新清零机会。

回退只移除 manifest 登记且摘要一致的退役入口/mask，恢复原 unit 和 runner 字节，执行配置加载核查后仍保持旧 timer disabled/inactive；新 timer 同时保持暂停。旧 program/unit 文件恢复、退役保护恢复情况及调度是否运行必须分别报告。发现未知 drop-in、被替换的 mask 或手工改动时停止覆盖；不能用通用 unmask/enable 操作绕过回退门槛。

## 15. 安全、运行路径与权限

### 15.1 拟议运行路径

| 路径 | 用途与权限原则 |
|---|---|
| `/usr/local/lib/vps-kit/releases/<version>/` | 不可变程序发行目录；仅 root 可写 |
| `/usr/local/bin/vps-kit` | 稳定入口，版本切换经 manifest 管理 |
| `/etc/vps-kit/traffic/` | 配置/修订/凭据引用；目录 0700、文件 0600，root 所有 |
| `/var/lib/vps-kit/traffic/` | 注册、账本、维护/迁移记录和备份；0700/0600 |
| `/run/vps-kit-traffic/` | 稳定执行/维护锁；目录与锁受保护，不随单次 service 结束删除 |
| `/run/vmiss-traffic-reset/reset.lock` | 仅接管 r2 后保留的兼容锁；与新锁共同使用，仅允许所需锁目录写入，不扩展为旧程序/账本写权限 |
| `/etc/systemd/system/vps-kit-traffic-<id>.*` | 工具拥有的 unit，0644；无凭据明文 |

### 15.2 传输与凭据

首版只访问本机面板。优先 HTTPS 并校验证书，域名/SNI 与连接地址分离时将连接限定到回环地址；支持显式选择回环 HTTP 以适配仅本机监听的面板，但不得把此选项用于非回环地址。禁止自动跟随重定向、关闭 TLS 校验或把失败请求回退到公网地址；不依赖宿主代理环境变量访问面板。

Token 经隐藏输入或受保护文件描述符传入，独立文件 root:root 0600，运行时使用 systemd LoadCredential。向 curl 通过受控标准输入传头，禁止把 Token 放在 argv、环境日志、unit、候选、报告或 Git。每台本机独立凭据；工具不替用户自动创建或扩大面板 Token scope。[3.10.2 Token 说明](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/docs/content/docs/en/reference/api/api-tokens.mdx)

运行用户首版为 root，配合 NoNewPrivileges、ProtectSystem、受限写目录等措施；这降低误写范围但不能抵御 root 或面板自身被控制。配置、凭据、账本和锁拒绝符号链接替换、非预期属主/权限与任意文件路径；版本入口和 unit mask 只允许 manifest 明确登记的目标，mask 必须指向 /dev/null，不能把受控链接规则推广到任意输入。路径、API 响应和日志均作为不可信输入，不执行它们携带的文本。

工具不额外执行 x-ui/Xray 启动或重启命令，不改防火墙、SSH、路由或系统时区；不默认发送遥测、通知或外部日志。自然清零调用可能通过面板自身逻辑触发 Xray 重启，见第 12 节；只读管理路径不调用这些写端点。HTTP 读回成功不是代理业务可用证明，实际业务保持人工验收。

### 16.3 双版本及真实副作用的重点

使用真实 3.7.0 创建数据库后迁移到 3.10.2，检查内嵌 settings、新字段、身份、配额与计数。`resetWeekday` 缺键兼容只有在该证据覆盖后才能开放；不得只改模拟 fixture 使测试变绿。

分别注入：Client POST 后入口被后台停用、入口 POST 后 Client 被禁用、HTTP 超时但队列之后提交、已完成账本配旧数据库。验证预期状态与不重发；数据库变化、API 变化和请求次数分别统计。记录组基线、last_traffic_reset_time 等服务端附带变化，无关对象设置哨兵，不把一切数据库变化都当错误或全部忽略。实际调用入口重置后观察待重启标记、后台处理及代理连接；不能因为工具未发送 restart 命令就跳过这项验证。

容量测试以 N=1、2、16 和受控延迟覆盖 240/300 秒边界。重置计数较小且新流量快速增长时必须允许“无法确认”并保留 pending；不引入更宽松零值判断来掩盖不确定结果。
